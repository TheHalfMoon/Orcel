# SG-000124 preparation: optional sandbox runtimes (SX-01 to SX-05)

**Status: PREPARATION ONLY.** This packet is not an activation. It adds no
crate, dependency, binary, capability or tool, and changes no spec state.
SG-000124 becomes active only through the SpecGrain process: an activation
spec, its own reviewed PR and the founder's decision. Sandbox **exposure**
(SX-06, MCP tools) is a separate grain, SG-000125, and needs its own
founder decision.

Backlog: `IMPLEMENTATION_BACKLOG.md` → SX-01 to SX-05. Roadmap: track S
("Sandboxes are explicitly not required for Core", ADVERSARIAL_REVIEW.md).

## Objective

Optional isolated workspaces for code execution behind a `Runtime` trait
(from cua-vmm): a rootless container backend on Linux first, then VM
backends (QEMU on all three hosts, Lume on macOS, Firecracker on Linux)
and a small in-guest agent. **Authority delta: none until SX-06.** The
runtimes are internal and unexposed under this grain.

## Dependencies to admit (each a reviewed decision in its slice)

- **SX-01:** a podman CLI subprocess at a pinned path, preferred over
  `bollard` (a large dependency, admitted only if the Docker API is
  chosen, with SBOM numbers). gVisor `runsc` is a user-installed
  prerequisite, never fetched at runtime.
- **SX-02:** QEMU binaries are a user-installed prerequisite or a
  separately admitted, pinned and checksum-verified download; never fetched
  at runtime.
- **SX-03:** the `lume` binary, verified by its code signature (as #487
  verifies browser bundles).
- **SX-04:** a pinned `firecracker` and `jailer`; donor crates kept at
  edition 2024 (toolchain 1.97.1 supports it).
- **SX-05:** no gRPC: the donor's tonic service is replaced by Orcel
  JSON-lines frames to keep the guest small.

## Security review (preparation)

| Risk | Treatment |
|---|---|
| Container escape to the host | Rootless only (no root, no setuid helpers), gVisor `runsc`; the contained tier's rules (XP-13) apply to the launcher |
| A guest that lies | The guest is untrusted: the host validates every reply (sizes, paths, exit codes) and never trusts guest-reported identity |
| Network egress from a sandbox | No network by default (Firecracker with the jailer, QEMU with no NIC, containers with `--network none`); any network is a later, governed decision |
| Exposed services (VNC, published ports) | VNC disabled by default and no published ports (SX-02) |
| Default credentials in upstream images (Lume) | Replaced before first use; documented upstream behaviour, never shipped |
| Supply chain of runtime binaries | Pinned versions, checksum or code-signature verification, no runtime downloads |
| Crash or partial sandbox state | SG-000120 journal and reconciliation for create and delete; a sandbox with an unknown outcome is reconciled before reuse |
| Resource exhaustion on the host | CPU, memory, disk and process limits per sandbox; bounded counts |
| Authority leaking before SX-06 | No tool, capability or MCP shape under this grain; a release-blocker test asserts no sandbox shape is reachable from orceld or MCP |

## Tests to write (SX-01 first)

- The Runtime trait round trip (create, exec, copy in and out, delete) on
  ubuntu-latest with rootless podman and runsc.
- Refusal paths: podman or runsc missing, an unpinned path, a root
  daemon: typed `ProviderUnavailable`, nothing started.
- No network inside: a connection attempt fails; no published port.
- Limits enforced: memory and process caps.
- Crash recovery: a killed host leaves no running sandbox after
  reconciliation.
- No exposure: no sandbox shape in orceld's dispatch or the MCP tool
  tables.
