## Why this needs governance

SG-000108's acceptance binds the live browser surface:

- **A13:** "Any live tool is a subset of the twelve SG-000079
  `browser_structured` shapes; the exposure profile, discovery,
  documentation and OAuth scope tables change together." The live MCP set
  today is six tools (`page_open`, `navigate`, `observe`, `click`,
  `download_preview`, `download`; `crates/orcel-browser-host/src/exposure.rs`).
  - **Already inside the twelve, held model-only by SG-000108 decision 4:**
    `browser.dom/fill`, `browser.upload/preview` and
    `browser.upload/submit` (`QUALIFIED_BROWSER_SHAPES`). Making them live
    is a promotion within the twelve, governed by A7 and decision 4, not
    an A13 widening.
  - **Outside the twelve, so exposing them widens A13:** select, check,
    press, hover, text waits, dialog accept, tabs, frame observation and
    the verifier.
- **A7:** exposure, discovery, documentation and OAuth scope tables must
  agree mechanically for any tool added, and remote mapping stays
  disabled.
- **A4:** frames, popups and workers obey the SG-000075 rules;
  `navigation::mediate_frame` (and `mediate_popup`, which calls it) allow
  the exact same origin only. BR-05 tabs (admitting a popup as a new tab)
  and any observation of **cross-origin** frames (E4) both relax that part
  of the acceptance.
- **BR-04 step 1** (an interactivity flag in observations) changes the
  observation contract that clients rely on.

## Security review (preparation)

| Risk | Treatment |
|---|---|
| Upload as data exfiltration | One host-staged file per approval, bound to the page origin, the form's submission target origin, and the file's name, type and SHA-256 (all shown to the person); a submission to any other origin is refused; the worker never sees a workspace path; STRONG for sensitive workspaces |
| Form fill of secrets into a hostile page | SOFT approval shows origin, element role and name and a value digest. **Open design question:** how a value is classified as secret (a value taken from the XP-19 secret store would be refused by provenance; free text has no reliable classifier). The activation spec must settle it |
| `press` causing an unapproved submission | A key press that submits or navigates is approved as that submission or navigation, with its target origin |
| Approval replay across pages or elements | The digest binds page generation, element identity (role and name, BR-01) and value; stale references are refused, never retargeted silently |
| Dialog spoofing (a page drawing a fake dialog) | Only engine-reported JavaScript dialogs are answerable; their text digest is in the approval |
| A `prompt()` answer as egress | The answer's digest is part of the approval; an answer other than the approved one is refused |
| Popup and tab admission widening navigation | Popups to non-admitted origins stay closed; admitted ones inherit the lifetime's pins and SG-000075 rules; host-issued tab ids |
| Cross-origin frame content leaking | Same-origin frames only unless the founder admits cross-origin observation (an A4 change); then only frames whose origin is admitted, with the same redaction as the main document |
| Clickjacking or covered targets | BR-04 refusal of covered targets stays in force for every pointer action |
| Contract drift between tables | A7's mechanical agreement test runs for each added tool |
| Remote reach | Remote mapping stays disabled; local-only, as SG-000108 |

## Recommended first activation (narrow)

**Proposal, not an activation.** Today an agent can open, read, click same-origin links and download, but cannot fill in a form. The smallest step that makes the browser useful for real work is **forms on admitted pages**, nothing else:

| Included | Slice | Why | Approval |
|---|---|---|---|
| Fill a text field | E1a | Promotion within the twelve shapes. Fields that **look** secret by their type, autocomplete, name or id are already refused (`isSecretField`). A secret typed into a field named `notes` is **not** detected, so this packet's open question stays open: the activation spec must say what the person is told | SOFT. Today's prompt shows a digest; showing the value is new work with rules for long values and control characters, because the approval binds text a dialog may cut off |
| Select, check | E1b | The rest of an ordinary form | SOFT per action |
| Press Enter | E1b | The way to submit. Today's `press` accepts any listed key on any element and only refuses Enter in a multi-line field, so an Enter-only, single-line limit is **new checks** | SOFT, stating that the page may submit or send what it holds. **The effect can't be known before the key**: a script can change the form's action or move focus. So enforcement is the route rule (one admitted destination per lifetime), and any origin shown is an unbound snapshot |
| Wait for text | E1b | Observation: the agent can tell the page changed | None |
| Postcondition verifier | E5 | Read-only: the agent checks its own result | None |

**Deferred:** other keys and hover, uploads (egress, E2), dialog accept (E3), frame observation (E4), tabs and popups (E6, which reverses A4) and the interactivity flag (E7). None of these is needed for forms on one admitted page.

**Unchanged:**
- `orceld` stays the sole approval and execution authority. Each action is approved one at a time, bound to the page generation, element and value.
- Local only: remote mapping stays disabled.
- Windows only until SG-000115 is activated.
- **Development builds only** until F4 slice 7 is decided. So this makes the browser usable for development and evaluation first.

**What it widens:** SG-000108 A13 (select, check, press, waits and the verifier are new shapes) and decision 4, which holds fill model-only. That is why it needs activation. A4 is untouched.

**A consequence to accept:** a page's own script can read a filled value and send it to its admitted origin without any submit. Approving a fill means trusting that page with that value.

**Cost:** none. **Reversible:** yes, the tools can be removed from the profile tables. **Not qualified:** no agent has driven these through orceld. The host and worker actions pass their native tests, but the orceld dispatch and MCP tools don't exist yet.

## Slice A6: Enter's route and the native run

**Engineering, on its branch.** The record of the change is `docs/security/SG-000108_PRODUCT_CALLER.md`, "SG-000122 slice A6". In short:

- An approved Enter may open one top-level document, a GET or POST on the page's committed origin, once, with redirects that stay on it (the Enter route rule, the spec's "enforcement is the route rule"). That document becomes the page's next generation, and the reply says `navigation: document_committed`.
- An Enter that opens nothing says `navigation: none`.
- Anything that leaves the origin (the form's action, a server redirect, a page script, a frame or a popup) is refused before it leaves and answers `CAPABILITY_DENIED`.
- Fill, select and check keep BR-02's no-new-document rule.
- The native run is part of `npm run browser-launcher:native`, which Windows CI requires. It covers the journey through orceld under the real broker and ledger, and the host-level route cases. **The consent is scripted** (the tests' decider approves each prompt and keeps what it showed), so CI proves the mechanism, not a person's approval.

## Founder-present run

**Status: PENDING, with the founder.** The spec's `done_when` names "each action approved by the person in orceld's broker with the value shown". CI's journey scripts that consent; an agent never answers Orcel's prompt, because that would be manufacturing consent. This run is the person's half. It needs a development build, because release builds carry no live browser (SG-000108 decision 7), and about 20 minutes at the prompt plus about 15 minutes to build.

**Before you start**

- Windows, at the keyboard, on your own unlocked desktop (the SOFT prompt is a Windows message box), with Microsoft Edge or Google Chrome installed.
- Node.js from the official installer under `C:\Program Files\nodejs`. A development build refuses a `node.exe` in a folder your account can change.
- A Rust toolchain (MSVC), Git Bash, and a checkout of `main` at a commit that includes this slice.
- Claude Code (`claude --version`), or another MCP client you can point at a local stdio server.
- Your existing Orcel configuration: the run uses your default workspace.

**1. Build the development browser.** In Git Bash, from the checkout:

```bash
npm ci
npm --prefix apps/orcel-browser-worker run build
npm run build --workspace @orcel/mcp
eval "$(node apps/orcel-browser-worker/scripts/dev-pin.mjs --node 'C:/Program Files/nodejs/node.exe' | sed 's/^/export /')"
cargo build -p orcel-browser-host --features live-browser-dev --bin orcel-browser-host
cargo build -p orceld --features live-browser-dev --bin orceld
```

`orceld` uses the browser host that sits beside it in `target/debug`. Rebuild both after any change to the worker, because the pin covers its files.

**2. Point the client at it**, with the browser profile chosen locally. For Claude Code, a project `.mcp.json` in a scratch folder:

```json
{
  "mcpServers": {
    "orcel-dev-browser": {
      "type": "stdio",
      "command": "node",
      "args": ["<checkout>/apps/orcel-mcp/dist/index.js"],
      "env": {
        "ORCEL_DAEMON": "<checkout>/target/debug/orceld.exe",
        "ORCEL_TOOL_SURFACE_PROFILE": "browser_structured"
      }
    }
  }
}
```

Start the client there, record its version, and check that its tool list shows `browser_fill`, `browser_select`, `browser_check` and `browser_enter`.

**3. The journey.** The page is a public test form, `https://www.selenium.dev/selenium/web/web-form.html`. It is a third party's page, so treat its names as untrusted. If it has changed or is down, use any public HTTPS form whose action is on its own site, and say which one you used. Paste these prompts one at a time, and **read each Orcel box before answering it**.

- **A. Open and observe.** *Using the browser tools: open a page, navigate it to https://www.selenium.dev/selenium/web/web-form.html, then observe it and list the form controls with their untrusted names.* Approve the navigation. Expected: names such as "Text input", "Password", "Dropdown (select)" and "Default checkbox", marked untrusted.
- **B. Fill, with one No.** *Fill the field named "Text input" with `Orcel A6 run`.* The box should show `Orcel A6 run` on the line after Target, and the field's role and name labelled page-supplied. **Click No.** Expected: `APPROVAL_DENIED`. Then: *Fill it again with the same value.* **Click Yes.**
- **C. A secret field.** *Fill the field named "Password" with `x`.* Expected: refused before any box appears.
- **D. Select and check.** *Choose "Two" in "Dropdown (select)", then check "Default checkbox".* Two boxes; each should show the option or the state. **Click Yes** on both.
- **E. Enter submits.** *Press Enter in "Text input", then tell me the reply's navigation and generation.* The box should warn that Enter may submit or send what the page holds, to the page's admitted origin. **Click Yes.** Expected: `navigation: document_committed`, a `url` on `www.selenium.dev` (`submitted-form.html` with the values in its query), and a generation one higher than before.
- **F. Wait and verify.** *Wait for the text "Received!" to appear, then verify that the URL is the one the reply gave and that the text "Form submitted" is visible.* No box. Expected: `met: true` and `verified: true`.
- **G. Stale.** *Fill "Text input" again, using the generation from before the submission.* Expected: `TARGET_STALE`, and no box.

**4. Evidence to post on #753** (a public issue):

- the client and its version, the commit you built, and the page you used;
- each step's tool result (Orcel's replies carry no page text beyond the untrusted names; check before posting all the same);
- a sentence for each box on what it showed: the value, the option, the state, Enter's warning, and the page-supplied name.

The journal (`orcel` task history) shows each step's outcome, and the approval ledger keeps each decision. Keep the client's transcript on your PC.

**Until then, this item is open:** no closeout may say a person approved a form action through a real client. The route rule's refusals (a cross-origin action, a redirect, a script) are proven by CI on the fixture and aren't repeated here, because a public page that leaves its own origin on purpose can't be relied on.
