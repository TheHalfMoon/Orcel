# SG-000115 preparation: browser host launch on macOS and Linux (XP-14)

**Status: PREPARATION ONLY.** This packet is not an activation. It grants
no authority, changes no spec state, and adds no capability. SG-000115
becomes active only through the SpecGrain process: an activation spec in
`.specgrain/specs/`, its own reviewed PR, and the founder's decision.
Until then, browser launch on macOS and Linux stays refused (the
`worker_launch.rs` fallback starts nothing, and the non-Windows
managed-policy check returns `Unreadable`, which fails closed).

Backlog entry: `IMPLEMENTATION_BACKLOG.md` → XP-14. Roadmap phase: X4.

## Objective

Bring the SG-000074..79 / SG-000108 browser host guarantees to macOS and
Linux. The host finds and verifies an installed Chrome or Edge, launches it
over the pipe with host-built argv, confines its network, supervises and
sweeps its process tree and profile, and the browser tools keep the same
policies on all three OSes.

**Authority delta (when activated):** the existing browser authority on two
more OSes. No new capability, tool, MCP shape or approval class.

5. Shutdown, cleanup, recovery and crash regression tests.

A component counts as inert only when all of the following hold:
- **Build-time exclusion.** It is compiled only into test builds (`#[cfg(test)]`) or behind a never-default feature. `orcel-browser-host` stays out of every release build: orceld reaches it only through the never-default `live-browser-test` and `live-browser-dev` features. The release-blocker sweep (`crates/orcel-lifecycle/tests/release_blocker_sweep.rs`) is green at the exact head.

- **Fail-closed behaviour, unchanged and pinned by tests:**
  - `engine_launch_admitted()` (`crates/orcel-browser-host/src/host.rs`) still refuses on macOS, and no new code path bypasses it or runs before it (`tests/sg000074_host.rs`);

- **No new or widened browser operation.** `apps/orcel-mcp/src/surface.test.ts`, `browser-exposure.test.ts` and `tool-contract.test.ts` pass unchanged at the exact head.
- **Source scan.** A test pins that only the component's own module and tests name it.
- **Test processes.** Inert tests may spawn only fixture or fake child processes. Starting a real Chrome or Edge on macOS or Linux, even on CI, is category B.
- **Windows unchanged.** Windows behaviour is unchanged.

Each slice still needs:

## Verified termination (A2b, inert preparation)

This addresses two open risks: the macOS descendant escape (founder decision 4) and the "verified coverage is never produced" gap that kept every A6 teardown holding the sink and the profile. It is inert: test builds only, fixture processes only, no production caller. It decides nothing reserved for the founder.

**Linux: a subreaper supervisor proves termination.**
- The supervisor is a dedicated process that sets `PR_SET_CHILD_SUBREAPER` before the engine starts.
- Every descendant that is orphaned is reparented to the supervisor, or to a subreaper that is itself a descendant. That includes a helper that called `setsid` or `setpgid` and whose parent then exited.
- `verified_sweep` repeats a cycle: kill every descendant it finds by parent links, then reap. It stops when `waitpid(-1)` returns `ECHILD`.
- A process with no children has no descendants, so `ECHILD` is the proof.
  - A fork after one scan is caught by the next round.
  - A descendant the sweep cannot kill (for example another user's, after a setuid exec) keeps it from reaching `ECHILD`. The deadline then returns `Incomplete`, so the incomplete coverage is detected rather than hidden.
- **Precondition:** the supervisor has no children other than the supervised family.
- **Tests,** run in a re-executed test binary, never the shared test process, with every fixture process's pid checked independently afterwards:
  - five escape shapes end `VerifiedComplete` with no survivor: setsid; setpgid; a double fork whose intermediate lingers; a double fork whose intermediate exits at once; a process that keeps forking setsid children during the sweep;
  - the same fast double fork without the subreaper leaves a real survivor, and the sweep reports `Incomplete`.

**macOS: parent unique-id lineage detects escapes, with one recorded limit.** Evidence: the PR's hosted macOS CI runs 41193328667 (head `66faabf0`) and 41194756639 (head `4ea89465`, green), re-run at each later head.
- `NOTE_TRACK` is unsupported: `kqueue_note_track_is_unsupported` passed, pinning `ENOTSUP`. This answers the packet's open question.
- Every process has a 64-bit unique id that is never reused. It also records the unique id of the parent that created it, which XNU keeps when the process is reparented. `the_parent_unique_id_survives_reparenting` passed: a setsid grandchild, reparented to launchd, still names its exited intermediate. The whole lineage rests on this.
- A tracker thread records the family's unique ids while it runs.
- At teardown the sweep repeats freeze, kill and confirm:
  1. closes the set over parent unique ids;
  2. **freeze:** sends `SIGSTOP` to every known living member on every round, because a member not yet stopped could continue another with `SIGCONT`. It stops only when one scan shows every known living member stopped (`SSTOP`). Stopped processes neither fork nor signal;
  3. **kill:** kills every member in that scan, then waits until each one has finished exiting. A process cannot finish exiting while a fork it started is still in progress, so any child it made already exists before the next listing;
  4. **confirm:** takes a fresh scan, repeated until no listed pid is gone at its read (a "torn" scan), and attributes it again. Coverage is verified only when the freeze converged, every killed member was seen to exit, the confirm scan is untorn, no known member is alive, and no scan of the sweep, freeze scans included, ever found an unattributable process. Otherwise the cycle repeats until the deadline, which ends `Incomplete`.
- On any error after a stop, every process the sweep stopped is killed, never left stopped.
- **The detection rule.** A process of any user is unattributable when it is not known and its creating parent was born after the root and is neither known nor alive. Any such process makes coverage `Incomplete`. There is no user filter: a setuid step in the chain must not hide a descendant.
- **Why the rule detects every escape that a scan reads.** A descendant's creating parent is the root or another descendant, so it is never older than the root. Follow a living descendant's ancestry upward. The topmost living, unknown ancestor below the last recorded member has a dead, unknown creating parent born after the root, so the rule flags it, whatever its user. The proof needs that ancestor to be listed and then read by a scan; see the recorded limit below. When it is read, the escape is detected and fails closed: the sink and the profile stay held.
- **What the rule never flags.** Anything that launchd or another process older than the root creates: XPC services, launch agents and apps.
- **Other users.** Another user's process whose unique ids can be read is a node like any other. It counts as a living parent and is flagged when unattributable. As a known member (a descendant that changed user) it can be neither stopped nor killed, so the sweep ends `Incomplete`. On the hosted runner launchd's (root's) unique ids are readable by the test user (`SG115-EVIDENCE … readable by this user: true`, run 41194756639).
- **The scan is not atomic; torn scans are rejected.** A scan lists pids, then reads each one. A process could fork after the listing and exit before its read, so its child is in neither; even one such hop (a daemonising double fork) would otherwise hide the child. A listed pid that is gone at its read makes the scan "torn", and the confirm scan is repeated until one is untorn. The hidden child is then listed and read, and flagged, because its creating parent is dead, unknown and born after the root. A chain that hops again in every scan keeps every scan torn, so the sweep ends `Incomplete` at the deadline. On a busy machine unrelated exits also tear scans; that only costs retries, or fails closed.
- **A pid reused within one scan is now torn too (B1, recorded before it was implemented).** If the hopping process's pid is taken by a new process before its read, that read finds a process, not a gap. B1 closes this with a clock mark. The scan reads the wall clock just before it lists pids. A listed pid whose process started at or after that mark was born after the listing, so the pid it was listed under belonged to a process that has since exited: the scan counts it as torn, exactly like a gap. The node itself is kept: it is a real process, attributed by its real ids and frozen and killed like any member, so freeze and kill coverage is unchanged. A process born between the mark and the listing is also counted, which only costs a retry. A test on macOS CI checks that a process started after a mark has a `pbi_start` at or after it (consistent with one clock), and the comparison is tested on every Unix; that `scan()` counts a real reused pid as torn is not exercised (a pid reuse cannot be forced), recorded as untested. Rule change: the confirm rule's definition of "torn" grows; nothing is relaxed. Residuals, recorded, not accepted: (a) a backward step of the wall clock during a scan could hide a reuse (NTP slews rather than steps in normal operation); (b) after a backward step at any time, processes whose start lies in the future tear every scan until the deadline, so the sweep ends `Incomplete` (fail-closed, never a false verification); (c) another user's process whose BSD info cannot be read has no start time, so it cannot be checked, and a descendant could reach that class through a setuid exec (part of the open "other users" item). A clock-independent alternative, if activation needs one: a unique-id high-water mark per scan (unique ids only grow; needs a fresh mark, e.g. a probe spawn, per scan) or the one-pass `sysctl KERN_PROC_ALL` snapshot.
- **Tests,** run alone in CI:
  - setsid, setpgid, a lingering double fork and a fork storm end `VerifiedComplete` with no survivor;
  - over five rounds of a fast double fork, any round with a survivor reports `Incomplete`. On the hosted runner all five rounds had a survivor and all five reported `Incomplete` (`verified=0 detected_incomplete=5`);
  - in that run, launchd's children caused no false positive.

**Open, not accepted.**
- **macOS false positives.** An unrelated process of any user can also make coverage `Incomplete`: one whose creating parent was itself started after the root and has exited (for example a command that double-forks, run from a terminal during the session). This is safe, but how often it happens on a real desktop must be measured before activation.
- **macOS other users.** A descendant that changes user through a setuid exec is followed only if its unique ids can be read. If they cannot, the lineage neither follows it nor flags it. Activation must close this; one option is to refuse an engine that can reach a setuid executable.
- **macOS check-to-kill window.** The unique id is re-checked just before each signal. A narrow window remains between that check and the signal; a pidfd closes the equivalent window on Linux.
- **Indirect spawning.** Work started on the engine's behalf by another process is not a descendant on either OS.
- **Activation's verified path.** Activation would run the host's sweep in a dedicated supervisor, matching the Linux precondition. Whether it does, and whether the A6 teardown may then release the sink and the profile on verified coverage, is category B.

## Network sink lifetime (A6b, inert preparation)

This addresses the sink-lifetime and port-reuse risk. It is still A6: test builds only, fixture processes only, no production caller.

**Now pinned by tests:**
- **A kept sink holds its port.** When teardown keeps the sink (coverage unverified), another process cannot bind `127.0.0.1:<port>`, even with `SO_REUSEADDR`, so nothing a surviving helper sends can reach it.
- **A freed port is free at once.** After the release step, another process can bind the port immediately. That is why the sink is released only on verified coverage, and last.
- **Verified release, end to end (Linux only).** Under a dedicated Linux subreaper supervisor (the A2b precondition), the rehearsal's teardown uses `verified_sweep` and really releases the sink and removes the profile. macOS teardown with the lineage sweep is not exercised here. This holds when a helper left the group, and when the engine crashed and orphaned a helper. The released port is then bindable. The rehearsal is otherwise unchanged: in the shared test process its sweep stays `Incomplete` and it keeps both.
- **The crash residual.** If the host process that owns the sink is killed while an orphaned helper keeps using the proxy endpoint:
  - the kernel frees the port at once;
  - another local process can bind it;
  - that process receives the helper's connections.

  A test pins this (`a_crashed_host_frees_the_port_while_an_orphaned_helper_still_uses_it`), so a mitigation is visible when it lands. That test must then be inverted, to become the mitigation's evidence, never deleted.

**Open, not accepted: the crash residual (risk 4).** No user-space step inside the host can run after the host is killed. Options for activation, each category B:
- **(a) Linux: a PID namespace.** The supervisor is the namespace's init, so the kernel kills every engine process when it dies. This needs user namespaces, which Ubuntu 24.04 restricts through AppArmor, or privilege. **B6b (investigation, test only):** `a_pid_namespace_init_takes_its_whole_family_with_it` enters an unprivileged user and PID namespace, makes the first child its init with a `setsid` helper below it, and kills the init: the helper must die with it. Each fixture records its host pid through the host's `/proc/self`. In a local run on WSL2 Ubuntu (not CI; unprivileged user namespaces allowed there) the helper was taken with the init. Where the host refuses unprivileged user namespaces (`EPERM`, `EACCES`, `ENOSPC` or `EINVAL` from `unshare`), the test records the refusal (`SG115-EVIDENCE unprivileged PID namespace refused`): that is evidence about the host, not a pass of the containment claim. Any other spawn failure fails the test (an exec failure that also returns `EACCES`, such as a non-executable `python3`, would be mislabelled as a refusal; it cannot occur on the CI runners). On the hosted Ubuntu 24.04 runner the expected outcome is AppArmor's refusal; the CI step "SG-000115 B6b PID namespace evidence (Linux)" prints the observed line on every run (it fails unless one of the two lines appears). Observed on the hosted Ubuntu runner (CI run 41399210347): `SG115-RESULT PID namespace: the init's death took its setsid helper: true`, so that runner allowed the unprivileged user namespace and the containment held there too. A host with AppArmor's restriction enabled would show the refusal instead; activation must check the deployment hosts. Rule change, recorded (SG-000085): A2's tests start one fixture in a new unprivileged user and PID namespace (`unshare` in `pre_exec`), test builds only. This is evidence for option (a), not a mitigation in place: the rehearsal still runs without a namespace, and the crash-residual test is unchanged.
- **(b) Linux: a delegated cgroup with `cgroup.kill`,** run by a watchdog outside the host. This needs systemd user-session delegation.
- **(c) Both OSes: the listening socket inherited by the engine family.** The port then stays bound while any holder lives. Chrome closes inherited descriptors in its helpers, so this covers the browser process only.
- **(d) The next start's recovery** kills the crashed run's orphans before anything else. This leaves the window between the crash and that start.
- **(e) Accept the residual,** which is a founder decision.

  the host contract is the same on all OSes; nothing in SG-000115 changes

## Linux S-07: hardening and what cannot be established

S-07 stays **not accepted**. This section records the hardening already made and the property that the Linux verifier still cannot provide.

**Hardening.** `discovery.rs`'s Linux verifier (from #488) now also runs `install_tree_trusted`. Its result is applied last: it can turn a verified engine into an unverified one, and a vendor package that fails the package check is still refused (`UnsupportedEngine`), exactly as before. What launch does with an unverified engine is unchanged:
- orceld reaches the browser only through the worker path, whose macOS and Linux fallback starts nothing;
- the classic host path refuses launch on macOS only (`engine_launch_admitted`), and is not reached from orceld.

The check requires:
- the engine, and every directory above it up to `/`, are owned by root, are not links, and are writable by neither group nor others;
- every entry in the install directory, walked without following links and bounded at 20,000 entries, is root-owned and writable by neither group nor others;
- every link inside the install directory is root-owned, and every hop of its chain is a relative name (no `/`, no `..`) that stays within the install directory.

**Why it matters.** `dpkg --verify` compares file digests at one moment, and it does not check modes. A file or directory that another account can write could be swapped after the check. For the engine's own install directory and the directories above it, the hardening closes that window against every account except root. Shared libraries, policy directories (`/etc/opt/chrome`) and fonts elsewhere on the system are not covered by this check.

**Tests.** `discovery_linux_tests.rs` runs on Linux wherever dpkg is installed, and on CI it fails rather than skipping if dpkg or Chrome is missing. Fixture modes are set explicitly, so the results do not depend on the umask. Each test builds a `google-chrome-stable` fixture package and installs it with an unprivileged dpkg into a private root (`--force-not-root --root`), so the real `dpkg-query -S` and `dpkg --verify` path runs end to end. The results:
- an intact package is verified;
- one changed byte in the engine or a library is refused;
- a file no package owns is not verified;
- a tree owned by another account is not verified;
- a group- or other-writable engine, library, install directory or ancestor is not verified, although dpkg itself reports the package clean;
- a link out of the install directory, or a chain through an outside hop, is not verified, while a relative link inside it is allowed;
- a tampered package whose files are also writable by others is still refused, not merely unverified;
- an engine path that is itself a link is not verified;
- on hosts with the real vendor package (CI's Ubuntu image ships Chrome), the verdict matches the install tree on disk, and the tree's state is printed as evidence.

Disabling the ownership check fails four of these tests: writable, link-out, other owner and link-chain.

**Evidence from the hosted Ubuntu runner, and a compatibility finding for the founder.** The stock GitHub Ubuntu image installs Chrome with `/opt/google` and its whole tree at mode `0777`, including the engine and the setuid `chrome-sandbox` (runs 41194327979 and 41293302923). Any account on such a machine could replace the engine, yet `dpkg --verify` reports the package clean, because it does not check modes. Under this hardening that Chrome is **unverified**. That is the case the check exists for, and it also means a standard hosted Ubuntu image would not launch Chrome at all. CI does not change the runner. On a host with Chrome, the real-tree tests assert the following:
- the package check passes by itself;
- the verifier's verdict matches the tree's state: unverified while the tree is writable by others, verified with the vendor's own modes;
- the tree problem is printed (`SG115-EVIDENCE`), shown in the log by a CI step that fails without it.

The positive path, where an intact package is verified, is shown with the fixture packages. There is no positive real-Chrome evidence on hosted CI.

**What cannot be established offline: a cryptographic link from the installed files to the vendor's signature.**
- dpkg records only per-file MD5 digests, copied from the package at install time. Nothing on disk is signed by the vendor.
- When apt installed the package from the vendor's repository, it checked the signed index (`InRelease`) and the package's SHA-256. Chrome is often first installed from a downloaded `.deb` instead (`dpkg -i` or `apt install ./file.deb`), and then no repository signature was checked at all.
- The `apt` front end and most images clean `/var/cache/apt/archives` by default, though `apt-get` does not. When the package file is gone, the chain cannot be re-checked without network access, and the agent must not use the network.
- The vendor repository carries only the current version. After `apt update`, the installed version's entry in `Packages` is often no longer there.
- Root can rewrite both the files and the database undetectably. On macOS, by contrast, root cannot forge an Apple-anchored code signature. Linux verification is therefore strictly weaker against a compromised root account or package manager. Against every other account, for the install tree and its ancestors, it is now as strong as file ownership.
- MD5 still resists second preimages in practice, but it is no longer a collision-resistant hash. This matters only if an attacker could influence the vendor's own build.
- On rpm systems the vendor's header signature and SHA-256 file digests are kept in the rpm database. `rpm -V` checks files against those digests. Re-verifying the header signature against a pinned key without the package file is not done here, and is a possible future step.

**A stronger option, which needs a founder decision.** A future inert slice could build a full cryptographic chain whenever the downloaded package, and the index entry for its exact version, are still present:
1. verify `InRelease` with `gpgv` against a pinned Google (or Microsoft) signing key shipped with Orcel;
2. take the package's SHA-256 from the signed `Packages` index, for the installed version;
3. hash the retained package file in `/var/cache/apt/archives` and compare;
4. hash every installed file with SHA-256 against the package's own `data.tar`, rather than relying on dpkg's MD5 `md5sums`;
5. require every entry in the install directory to be listed by `dpkg -L`, because `dpkg --verify` ignores extra files, and an attacker with root (the threat this chain targets) could add one.

When the package file or the index entry is missing, or the package was installed from a downloaded `.deb`, the engine would stay unverified. The activation would have to choose between:
- (a) keeping Linux refused;
- (b) accepting S-07 with this hardening, the founder decision;
- (c) requiring the retained-package chain above;
- (d) another vendor-provided signature, if one becomes available.

## Profile cleanup hardening (A3b, inert preparation)

This addresses the profile-cleanup risk. It is still category A3 and A5: test builds only, no production caller, and it accepts nothing reserved for the founder.

- **Symlink swaps anywhere in the path.** `ProfileHold::open_beneath(state_root, relative)` opens every component below a trusted state root relative to the one before it, with `O_NOFOLLOW | O_DIRECTORY`. A link at any component refuses, and so do `..`, `.` and absolute parts. `open` checks the last component only, and a test shows it following a middle link that the walk refuses.
- **Owner validation.** The state root and every directory between it and the profile must belong to this user and be writable by neither group nor others. A test-only override of the expected owner (`with_expected_owner`) shows that another account's profile is refused by both `open` and the walk. Writable ancestors are refused.
- **Crash recovery and incomplete teardown.** The Orcel lock is `O_CLOEXEC`, so an engine never holds it. Before, recovery after a host crash would therefore call a profile stale and delete it under a browser that was still running. `recover_stale_profile` now keeps the profile (`EngineMayBeAlive`) in these cases:
  - Chromium's `SingletonLock` names a live pid on this host;
  - it names another host;
  - it is not a link;
  - its target cannot be parsed;
  - on Linux, a process carries `--user-data-dir=<profile>`, which covers an engine that has not yet written its lock. The flag is matched as a NUL-separated argument or as a space-separated token, because Chromium rewrites its process title into one space-joined string. Both the given and the resolved spelling of the path are matched. A process whose command line cannot be read (for example under `hidepid=`) counts as an engine that may be alive. Matching against a real Chrome is still to be confirmed before activation.
  A dead pid on this host lets recovery remove the profile. A reused pid can only keep a profile, which fails safe. A6's start refuses on `EngineMayBeAlive`, as it does on `InUse`.
- **Tests:**
  - another account's profile is refused, both opened directly and through the walk;
  - a middle-component link is refused by the walk;
  - `..`, `.`, absolute and empty paths are refused;
  - a group- or other-writable intermediate directory or state root is refused;
  - a live, foreign-host, unparseable or regular-file `SingletonLock` keeps the profile, and a dead pid removes it;
  - on Linux, a running process named with the profile keeps it, and it is removed once that process exits.
  Disabling the walk's ancestor check, or the engine check, fails three of these tests.
- **Open, not accepted:**
  - ~~macOS has no command-line scan~~ closed by B2 (below) for this user's processes; another user's engine is still not seen on macOS;
  - an engine in another PID namespace (Flatpak, containers) writes a pid that `kill(pid, 0)` cannot check here, so its profile could be removed while it runs;
  - a profile path containing a space never matches the space-token form of the command-line check (since B2 it matches as a whole argument, which covers macOS and a Linux title that was not rewritten), so on Linux a rewritten title leaves only `SingletonLock` to protect it. Activation must refuse such profile paths, or match differently;
  - under `hidepid=1` every other user's command line is unreadable, so recovery always keeps the profile. That fails safe, but it leaks profiles until they are removed by hand;
  - a renamed host, or a `SingletonLock` target longer than the read buffer, keeps the profile forever. That is safe, but it leaks;
  - since B5 (below) recovery can run through the walk (`recover_stale_profile_beneath`), and the final directory is then removed relative to its held parent; since B5b `recover_stale_profile` runs through the walk anchored at the profile's parent, and A6 holds its profile with `open_beneath` from the parent, so recovery, the hold and teardown's final removal all go through it (the parent must be private; the path-based `open` remains only for its own tests);
  - macOS ACLs: closed by B6a (below), which refuses any allow entry;
  - `verify` still re-checks the path by name (for a walked hold it also checks the name under the held parent, B5).

### B2: the macOS command-line scan (recorded before it was implemented)

- **Gap closed.** On macOS an engine that has not yet written `SingletonLock` was not seen, so recovery after a host crash could delete its profile under it.
- **Fix.** On macOS, recovery now lists every pid (`proc_listallpids`) and reads the arguments of each process of this user with `sysctl KERN_PROCARGS2`. A process whose arguments name the profile as `--user-data-dir=<profile>` (the given or the resolved spelling, as on Linux) keeps the profile (`EngineMayBeAlive`). The match now also accepts a whole NUL-separated argument, not only a space-separated token, on both systems: a profile path with a space matches as a whole argument (always on macOS, which does not rewrite process titles; on Linux unless the title was rewritten into one space-joined string). This only adds reasons to keep a profile.
- **Fail-safe rules.** A process of this user whose arguments cannot be read, or come back malformed, counts as an engine that may be alive. So does a process whose owner cannot be read for any reason other than "no such process" (gone) or "permission denied" (another user), including a short read, and a listing that fails or reaches its bound. A process that exited between the listing and the read, or is a zombie, does not.
- **Rule change, recorded.** The inert cleanup module gains two read-only macOS calls, `proc_pidinfo(PROC_PIDTBSDINFO)` for the owner and status and `sysctl(KERN_PROCARGS2)` for the arguments, and one more reason to keep a profile. Nothing is removed or relaxed, and the module stays in Unix test builds only.
- **Tests.**
  - The Linux test of a running process named with the profile now also runs on macOS CI: the profile is kept while the process runs and removed once it exits.
  - The `KERN_PROCARGS2` layout parser is tested on synthetic buffers on every Unix: argc, the executable path and its padding, truncation and a bad argc.
- **Open, not accepted.** Another user's process, root's included, cannot be read without privilege, so another user's or a root-run engine is not seen on macOS (a 0700 profile is usable only by its owner or root). The same holds on Linux under `hidepid`. B2's macOS behaviour rests on hosted macOS CI. B2 read "permission denied" on a process's BSD info as another user's process, which a sandboxed host could get for its own engine; B3 (below) closes this: this user's processes now come from the kernel's own list for this uid, so a refusal no longer decides ownership.

### B3: this user's processes come from the kernel's own list (recorded before it was implemented)

- **Gap closed.** B2 read "permission denied" (`EPERM`) on a process's BSD info as another user's process. A host running under a sandbox (App Sandbox or a seatbelt profile) can be refused its own engine's info, so recovery could skip that engine and delete its profile.
- **First attempt, rejected by CI.** Treating every refusal as "keep" failed on hosted macOS: an unprivileged process is refused the BSD info of every other user's process (launchd's included), so recovery would have kept every profile forever. The premise test caught it, and four recovery tests failed. That design is not used.
- **Fix.** This user's processes are the ones the kernel lists for this effective uid (`sysctl KERN_PROC_UID`, served to an unprivileged process, as for `ps`). Only those are examined: their arguments are read with `KERN_PROCARGS2`, as in B2. A process outside the list is another user's by the kernel's report, never inferred from a refusal. The list's records are `struct kinfo_proc`; only `p_stat` and `p_pid` are read, at fixed offsets. The record size comes from a real read of this process's own record, which must carry this process's pid (a size query alone reports spare room, so it is not used; found in review). The layout is checked at run time: the records must divide the reply exactly and must name this process as running, or the list is not used. A macOS test pins the record size at 648 bytes.
- **Fail-safe rules.** A list that cannot be read, is torn, exceeds its bound or fails the layout check keeps the profile. A process of this user whose arguments cannot be read or parsed keeps it. Zombies (`SZOMB`) and processes that exited before their read do not.
- **Rule change, recorded.** The macOS scan now reads two more `sysctl` names (`KERN_PROC_PID` for the record size, `KERN_PROC_UID` for the list) and no longer uses `proc_listallpids` or `PROC_PIDTBSDINFO`. Nothing is relaxed.
- **Tests.**
  - Every Unix: the record parser on synthetic lists (this process required and not a zombie; torn, empty, short-record and over-bound lists refused).
  - macOS CI: the kernel serves the list without privilege; it names this process and a child of it, and not launchd.
  - macOS CI: the test binary is re-run under `sandbox-exec` with `process-info-pidinfo` denied. Inside, the engine's BSD info is refused (so B2 would have skipped it), the list is still served and names the engine, and its profile is kept (`B3-RESULT refused=true listed=true named=true`).
  - The B2 recovery tests still show a profile removed once its engine exits, so other users' processes do not keep it.
- **Spawn rule change, recorded (SG-000085).** A5's test module, admitted until now as a fixture spawner only, also re-runs one test of the test binary (`unix_cleanup::tests::b3_sandboxed_entry`, `--exact`) under `/usr/bin/sandbox-exec`, as A2b re-runs it as a supervisor. The tripwire's comment records it. Test builds only.
- **Open, not accepted.** A sandbox that also hides this user's process list or every process's arguments keeps every profile: safe, but recovery then never removes one. An engine that starts after the list is read is not seen by that scan (as before; `SingletonLock` still covers a started engine).

### B5: recovery through the held walk (recorded with the change)

- **Gap closed.** Recovery opened a profile by path and removed its directory with `rmdir(path)`, so a swapped ancestor between the check and the removal was resolved again by name. What remains: the name can still be swapped inside the held parent between its check and `unlinkat`; the parent is private to this user and `AT_REMOVEDIR` removes only an empty directory, the same bound as before.
- **Fix.** `recover_stale_profile_beneath(state_root, relative)` holds the profile through `open_beneath`, which opens every component with `O_NOFOLLOW` below a trusted state root and refuses `..`, `.`, absolute and empty parts. The hold keeps the profile's parent descriptor and name. `verify` then also checks that the name under the held parent still names the held directory and that the parent is still private. The final directory is removed with `unlinkat(parent, name, AT_REMOVEDIR)`, never through a re-resolved path.
- **Rule change, recorded.** A walked hold keeps one more descriptor (its parent), and recovery gains an anchored variant. A platform error from the final `verify` inside the removal is now reported as `CleanupError::Platform` rather than wrapped as `Profile(Platform)`. Nothing is relaxed: the path-based `open` and its removal are unchanged, and nothing production calls either.
- **Tests (Linux and macOS, in the main Rust job).** A stale nested profile is removed and its parent kept; a link in place of an intermediate directory refuses without touching the data behind it; `..`, `.`, absolute and empty relative paths refuse; an intermediate directory swapped for a link after the hold makes the sweep refuse (`Swapped`; the existing by-name check catches this one); and the case only the held parent catches: the profile moved to another directory and linked back under its old name, so the path still names the held directory, is refused (`Swapped`) and nothing is removed, where the path-based removal would have removed it.
- **Process note.** The PR was opened by another session with its tests first; the record here was added on review, before merge. A separate workflow it added duplicated the main Rust job and was removed.
- **B5b (recorded with the change).** `recover_stale_profile(path)` now walks from the profile's parent (`recover_stale_profile_beneath(parent, name)`), and A6's start holds the profile with `open_beneath(parent, name)`, so its teardown removes the profile relative to the held parent. Rule change: the profile's parent must now be a private directory (this user's, not group- or other-writable, no allow ACL on macOS); a profile path without a usable parent (the root, a `..` ending, or a bare relative name, whose parent is empty) refuses, never reported absent. Nothing is relaxed. Cost, recorded: a profile directly under a shared directory such as `/tmp` (1777), or under a symlinked parent, is now refused and left in place instead of removed.

### B3b: a dying process does not keep a profile forever (recorded with the change)

- **Found.** Main CI for the B6b handoff (#576, run 41437278517) failed the A6 rehearsal on macOS: recovery answered `EngineMayBeAlive` for a profile no engine used. In the shared test process other tests start and kill fixture processes concurrently; the likely cause (not proven from the log) is a process of this user caught while exiting, whose `KERN_PROCARGS2` read failed with an error other than `ESRCH`, which B3's fail-safe rule counted as a possible engine. Neither B4's root check nor `SingletonLock` applies in that test.
- **Fix.** After a failed or unparseable arguments read, recovery re-reads that process's own kernel record (`KERN_PROC_PID`). It keeps the profile only when the process is still listed and not a zombie, or when the record cannot be read or does not check out. A process the kernel reports gone (`ESRCH`, an empty record) or a zombie no longer keeps the profile. Rule change, recorded: one more read-only `sysctl`, and a narrower reason to keep a profile, bounded by the kernel's own report. A process that is genuinely alive and unreadable still keeps it.
- **Test (macOS CI).** This process and a running child are living; a killed, unreaped child (a zombie) and a reaped one are not.

### B4: a root-run engine keeps every profile (recorded before it was implemented)

- **Gap narrowed.** On macOS another user's arguments cannot be read without privilege, so recovery cannot tell which profile another user's engine uses. A profile is 0700, so by its mode only its owner and root can use it: the other engine that matters is a root-run one. This rests on no ACL granting another user access; macOS ACLs on profiles are not inspected yet (A3's open item), so a profile with such an ACL is outside B4's reasoning.
- **Fix.** Recovery reads root's process list from the kernel (`sysctl KERN_PROC_UID` for uid 0, served to an unprivileged process, as for `ps -U root`) and each record's process name (`p_comm`, the executable's name cut to 16 bytes). While any living root process's name starts with an engine name XP-14 discovers (`Google Chrome`, `Microsoft Edge`), or with `Chromium`, every profile is kept. Matching by prefix also covers their helpers' cut 16-byte names and variants such as `Google Chrome Canary`. The name field's position is checked at run time: this process's own record must carry its own executable's name, or the record size check fails and every profile is kept.
- **Fail-safe rules.** A root list that cannot be read, is torn, exceeds its bound or fails the layout check keeps every profile.
- **Rule change, recorded.** One more read-only `sysctl` list (root's) and one more reason to keep a profile. Nothing is relaxed. The cost: a root-run browser blocks recovery of every profile until it exits.
- **Tests.** Every Unix: engine names (helpers' cut names included) and non-engines; the name field on synthetic records (its NUL, its 16-byte limit, zombies, torn and over-bound lists). macOS CI: root's list is served without privilege, names launchd, holds no engine on the runner, and recovery is not blocked there. A root-run engine itself is not started in CI (it would need privilege); its recognition rests on the synthetic records.
- **B3's sandbox test, kept honest.** Because B4 keeps every profile whenever its root check fails, the sandboxed re-run also asserts that the root check found no engine (`B3-RESULT refused=true listed=true root_engine=false named=true`), so the kept profile still comes from matching the engine.
- **Open, not accepted.** A root engine under another name (a renamed or unlisted browser) is not recognised. Another non-root user's engine could use the profile only through an ACL; since B6a a macOS profile with any non-deny ACL entry is refused.

### B6a: macOS ACLs on the profile (recorded before it was implemented)

- **Gap closed.** On macOS an extended ACL can grant another user access whatever the mode bits say, so exactly 0700 / 0600 did not exclude other users (A3's open item, which B4's reasoning rests on).
- **Fix.** The hold reads the extended ACL through each descriptor (`acl_get_fd_np`, `ACL_TYPE_EXTENDED`): the profile directory, its lock file, and every directory the walk crosses below the state root, and the state root itself. Its entries are walked with the ACL library's own calls (`acl_get_entry`, `acl_get_tag_type`), and any entry that is not a deny entry (`ACL_EXTENDED_DENY`) refuses (`Permissions`): an allow entry, or a tag not known to be deny. Rendered text is not parsed, so flags such as inheritance or `inherited` cannot hide an allow entry (found in review). No ACL, or a deny-only one, is accepted, since macOS itself puts "everyone deny delete" on home folders. An ACL that cannot be read, or one with more than 128 entries, refuses. `verify` repeats the check, so an allow entry added after the hold is caught.
- **Linux.** POSIX ACL entries are bounded by the mask that the mode's group bits carry, which the mode checks already constrain, so no change there.
- **Rule change, recorded.** Four more read-only macOS library calls (`acl_get_fd_np`, `acl_get_entry`, `acl_get_tag_type`, `acl_free`) and one more reason to refuse a profile. Nothing is relaxed.
- **Tests.** Every Unix: the tag rule (deny-only accepted; allow, undefined and unknown tags refused). macOS CI: a real "everyone allow read" ACL on the profile, on its lock, or on an ancestor refuses; an allow entry the profile inherits from its parent (set with inheritance flags) refuses; one added after the hold is caught by `verify`; a deny-only ACL is accepted.
- **Open, not accepted.** Directories above the state root are not inspected (the state root is the trusted starting point). On Linux, NFSv4 or richacl filesystems are not bounded by the mode bits and are not inspected.
