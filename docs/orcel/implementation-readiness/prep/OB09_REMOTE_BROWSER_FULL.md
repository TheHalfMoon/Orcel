## 2. Design

```
ChatGPT -> Secure MCP Tunnel set up for browser_full -> orcel-mcp-host (authenticated remote context; the relay serves core only)
  -> orceld profile gate: remote context names browser_full, shape is remote-safe
  -> SG-000055 remote-session lease (STRONG-created, browser_full profile, scopes, workstation, trust)
  -> broker as client "remote:<connection>:<principal>:<MCP session>", approvals stamped remote
  -> live browser: the Windows dialog for each open, click, fill, select and new tab with a URL (no lease covers a remote session)
  -> receipt names caller {kind: remote, provider, device, connection}
```

**Remote-safe tools.** Each was decided from the specs:

| Tool | Shape | Remote scope | Why |
|---|---|---|---|
| `browser_session_create` | `create` | `orcel.execute` | A Shadow session raises no dialog (section 1). Ephemeral profile only. Naming a persistent profile is refused, because it may be signed in to the owner's accounts. Visible mode still asks the owner first. |
| `browser_open`, `browser_click`, `browser_fill`, `browser_select` | `open`, `click`, `fill`, `select` | `orcel.execute` | Each asks its own SOFT approval; no lease covers a remote action (section 1). Secret fields are refused. |
| `browser_tabs` | `tabs` | `orcel.execute` | Only a new tab with a URL asks (SOFT, as `browser_open`). A new blank tab, list, switch and close raise no dialog (section 1). |
| `browser_close` | `close` | `orcel.execute` | Ends the caller's own session, with no dialog (section 1). A window a person is using is never closed (OB-06). |
| `browser_snapshot`, `browser_verify`, `browser_extract`, `browser_screenshot`, `browser_task_status` | `snapshot`, `verify`, `extract`, `screenshot`, `status` | `orcel.read` | Reads of the caller's own session page. Screenshots mask secret fields, and URLs go through `agent_url`. |
| `browser_profiles`, `browser_profile_create`, `browser_profile_delete` | `profiles`, `profile_create`, `profile_delete` | local-only | These manage profiles that may hold the owner's sign-ins, and delete is destructive. |

No tool types into a secret field, handles a credential, or evaluates page script. `evaluate_in_page`, `credentials`, `payment_cards`, `solve_captcha` and `run` stay excluded. Uploads stay model-only and have no `browser_full` tool.

**Where the code is:**

- `crates/orcel-policy/src/remote_session.rs`. `browser_full` is now a second remote tool-surface profile (`REMOTE_PROFILES`). `required_browser_full_scopes` maps the twelve remote-safe shapes. `check_remote_dispatch` picks the scope table by the lease's own profile, so a `core` lease never covers a broker shape and a `browser_full` lease covers nothing else. `build_lease` accepts `browser_full`, under the same STRONG-gated local command. Its prompt names `profile=browser_full`. The core table and its cross-language test are unchanged.
- `crates/orceld/src/profile_gate.rs`. `REMOTE_BROWSER_FULL_SHAPES` lists the remote-safe shapes. A remote broker request passes the gate only when its authenticated remote context names `browser_full`, the shape is remote-safe, and `create` names no persistent profile. A local request whose MCP session id starts with `remote:` is refused, so it cannot pose as a remote client.
- `crates/orceld/src/sg000039_main.rs`. A remote broker request goes through `remote_session_gate` (the SG-000055 check, now shared with the core path) and then `handle_browser_full`. Its approval broker is the existing `OriginStamp`. Every prompt it raises is the owner's Windows dialog, marked remote with the provider, device and connection taken from the authenticated context. Nothing the remote caller sends can answer a prompt: the shapes take no approval or token field, and approvals come only from the local broker.
- `crates/orceld/src/browser_remote.rs`. `Caller` (local or remote). The broker client is `remote:<paired connection>:<principal>:<MCP session>`, so a remote client never reaches a local session or another remote client's session. Its `client_ref` is the remote kind, which no lease can name. `refuse_remote_profile` refuses persistent profiles a second time, after the gate.
- `crates/orceld/src/browser_lease.rs`. `FullAccess::for_remote_caller` marks a remote session, which no lease ever covers: every decision asks and every confirm refuses `lease_invalid` (CAPABILITY_DENIED, an existing code), before the service is read, and `browser_task_status` shows no lease for it. `FullAccess::for_session` picks this from the request's caller, and from the `remote:` broker client as well, so either is enough (`ob09_a_remote_callers_session_gets_the_remote_lease_cache`; both call sites are pinned by `the_live_dispatch_wires_the_reopen_and_the_caller`). The issuer and client-match rules that #836 added for remote sessions are removed, because nothing reaches them; `check_browser_lease` still binds every local lease to its client. For local sessions the routine and high-impact classification, the takeover gate, the epoch and revoke checks, and the service's audit-first `Authorize` are unchanged.
- `crates/orcel-policy/src/browser_lease.rs`. A remote broker client's reference is its own kind, `cl-remote-` and 32 hex (`client_ref`), which `is_client_ref` refuses. So no lease can name a remote client: the CLI (`orcel browser grant`, with a message that says why), the service's scope check and orceld's admission each refuse it. This is defence in depth beside the rule above.
- `crates/orceld/src/browser_broker.rs` and `browser_receipts.rs`. Each session keeps its `Caller`. Its `session_start` event, every intent and every receipt carry `caller`: `{"kind":"local"}`, or `{"kind":"remote","provider","device","connection"}`. Each digest covers it.

- `crates/orceld/src/browser_broker.rs` (`needs_you_json`). In a remote caller's session, each Needs-you entry also carries `remote_caller` (provider and device, from the authenticated remote context, as the approval prompt's Origin line does). Its guidance says that a remote client drives the session, not someone at this PC, and that once the person completes the page (a sign-in included), that remote client acts in it as the signed-in account until the session ends. It never points at a persistent profile. The remote caller's reply carries nothing from the person's sign-in: only fixed words, the page id and the detector's closed signal names. Later replies show page URLs through `agent_url`, which masks query and fragment values after a sign-in.

**What is unchanged:** OB-06 takeover, OB-07 handoff (`HUMAN_VERIFICATION_REQUIRED`, which is refused before any lease is consulted, with the same failure code and handoff values), OB-07b sign-in and `agent_url`, the Shadow and Visible mode rules, and every local behaviour except the `remote:` prefix refusal. A local session's Needs-you entry is unchanged.

## 3. Threat model

**No lease covers a remote session** (section 1), and the rule is structural in three places. orceld decides "ask" for a remote session before it reads the service, and refuses at confirm a lease use that somehow got there. A remote client reference (`cl-remote-...`) is not one any lease scope accepts, so the CLI and the service issue none for it and orceld admits none. A lease that names a local client never matches a remote session, and a remote caller never reaches a local session (`remote:` broker client).

| Threat | Mitigation | Test |
|---|---|---|
| A remote caller with no STRONG remote-session lease drives the browser | The SG-000055 check runs after the profile gate and before anything else, and fails `REMOTE_SESSION_INACTIVE` | `ob09_remote_browser_full_without_a_strong_session_lease_is_refused` (policy), `ob09_remote_browser_full_without_a_strong_session_lease_never_reaches_dispatch` (orceld) |
| A `core` remote lease or token reaches browser tools, or a `browser_full` lease reaches files or processes | The scope table is chosen by the lease's profile, and lease and context profiles must match | `ob09_core_and_browser_full_leases_never_cover_each_other`, `ob09_a_browser_full_session_lease_covers_only_the_remote_safe_broker_shapes` |
| A remote caller uses or deletes a signed-in persistent profile | Gate, handler and dispatch each refuse it | `ob09_a_remote_session_never_names_a_persistent_profile`, `ob09_a_remote_caller_never_uses_a_persistent_profile`, `ob09_remote_browser_full_reaches_only_the_remote_safe_shapes` |
| Any lease covers a remote action | `decide` asks and `confirm` refuses for every remote session, with no service read and nothing authorized; local coverage is unchanged | `ob09_a_remote_session_is_never_covered`, `ob09_local_coverage_is_unchanged` |
| The owner grants, or something forges, a lease that names the remote client | The remote client reference is refused by the CLI, the service's scope check and admission; a forged one still covers nothing | `ob09_no_lease_can_name_a_remote_client`, `sg132_browser_grants_are_one_session_exact_origins_routine_families`, `client_refs_and_session_ids_have_one_shape`, `ob09_a_remote_client_is_bound_to_its_connection_and_principal` |
| A remote caller submits, buys, publishes or deletes without the owner | No action is covered; the actions that ask (section 1) ask on the Windows dialog, marked remote | `ob09_a_remote_session_is_never_covered`, `a_remote_requests_approvals_are_marked_remote` (existing) |
| A local process poses as a remote client to reach its sessions | Local ids with the `remote:` prefix are refused | `ob09_local_browser_full_is_unchanged`, `ob09_local_callers_are_unchanged` |
| Receipts cannot tell a remote action from a local one | `caller` is in every intent, receipt and session start, and digest-covered | `ob09_receipts_carry_the_remote_origin`, `ob09_receipts_name_the_remote_origin` |
| The person signs in for a session without knowing that a remote client will then drive it, or the remote reply leaks something from that sign-in | Remote Needs-you entries name the remote provider and device and say that the remote client then acts in the page; the entries hold fixed words only; URLs are masked after a sign-in | `ob09_a_remote_sessions_handoff_names_the_remote_client_and_carries_nothing_from_the_sign_in` |
| Routine remote opens, clicks, fills and selections prompt every time (FA-D usability) | Accepted: the founder's decisions of 2026-11-23 (section 1) | none (the cost of the decision) |

## 4. Residuals

- **UNVERIFIED (founder run).** No real ChatGPT run has happened. It needs the founder at the PC for every owner step: `orcel tunnel setup --profile browser_full`, a STRONG remote-session lease from `orcel tunnel allow`, and the dialogs (section 1; `orcel browser grant` refuses a remote session's client reference). ChatGPT must also allow write tools in the founder's plan, and Orcel cannot turn them on.
- The remote-session lease lasts at most 15 minutes (SG-000055), and a reconnect does not extend it. A long remote task needs a new lease.
- **The remote-session lease store is JSON with an unkeyed checksum.** `remote_leases.json` (`crates/orcel-policy/src/remote_session.rs`) holds the SG-000055 leases with a plain SHA-256 checksum, which detects corruption, not tampering: anything running as the owner's Windows user can write a lease with a matching checksum, and the path has an override (`ORCEL_REMOTE_LEASE_PATH`, which must be in a private directory). So the STRONG approval at `remote.lease.create` protects against remote and agent callers, not against a malicious local process of the same user. With no remote coverage, a forged `browser_full` lease still reaches no page action that asks without the owner's dialog; it does reach the caller's own ephemeral Shadow session (create, reads, close). Moving this store behind the SG-000132 service is future work.
- **The remote-session lease store's updates are not serialized** (pre-existing, SG-000055; not fixed here). orceld creates, revokes and pins leases with a load, a change and an atomic save, with no lock across processes, so two orcelds updating at once can lose one update: a revoke can be undone by a concurrent create or pin that loaded the file before it. The lifecycle lock orders `orcel tunnel` commands only. A lost revoke ends with the lease's own expiry (at most 15 minutes).
- No live-browser run was made with a remote context. The Windows `live-browser-dev` build compiles and passes clippy, and the remote path reuses the same live code as the local one.
- The OAuth scopes are reused (`orcel.read` for reads, `orcel.execute` for actions). There is no browser-only scope. The separation comes from the `browser_full` tool-surface profile, which the tunnel setup and the STRONG lease bind. A dedicated scope would need SG-000054 vocabulary changes in the relay and the OAuth server.
- **Tunnel only** (engineering-chosen 2026-11-22, matching the founder's directive of ChatGPT through the Secure MCP Tunnel). The relay registers every OAuth client as provider `generic` and cannot tell ChatGPT from another client, so the relay never serves `browser_full`: `orcel remote pair --profile browser_full` is refused with a message that points at the tunnel, the relay refuses a pairing offer that names any profile, the relay edge and the device uplink check tools against `core` only, and a relay paired connection holds `core` only. A remote ChatGPT session that uses the relay instead of the tunnel gets the core profile.
- High-impact signals are still the OB-08 heuristics (open choice 4). Locally, an action that is wrongly classified routine would be covered; remotely nothing is covered. The host's GET-only binding while covered actions run still blocks a non-GET request.
- A per-request read mode asks for each remote read, which makes snapshots slow. A session read mode is the owner's choice at lease creation.

## 6. Part 2: the remote profile through the ChatGPT Secure MCP Tunnel

**Tunnel only, one profile per tunnel, chosen by the owner on the PC** (engineering-chosen 2026-11-22). A ChatGPT Secure MCP Tunnel serves exactly one remote profile: `core` (the default, unchanged) or `browser_full`. The relay serves `core` only. Nothing remote can choose, enroll or widen a profile.

- **Tunnel** (`crates/orcel-lifecycle/src/tunnel_route.rs`, `config.rs`, `commands.rs`, `mcp_host.rs`). `orcel tunnel setup --profile browser_full` records `profile` in the tunnel settings (`core` is the default and is never written). `route_for` derives a `browser_full` route with its own remote connection id and client profile (`chatgpt-secure-mcp-tunnel-browser-full`) and the scope ceiling `orcel.read orcel.execute`, never `orcel.write`. So a core lease never covers it, and `orcel tunnel allow` (STRONG) leases its own connection. `orcel-mcp-host` passes that route down. The core route and its ids are unchanged and pinned. `orcel tunnel revoke` revokes both derived connections (core and `browser_full`), trying the second even if the first fails, and a `tunnel setup` that changes the tunnel id or the profile revokes every derived connection of the previous tunnel. The old route is revoked before the new one is saved, so a failed revoke saves nothing and a crash in between leaves the saved setup naming the old id, which a rerun or `orcel tunnel revoke` still reaches. Both commands say which connection's leases ended and which could not be ended (and may still be active until they expire, at most 15 minutes), or could not be confirmed as ended. "Not revoked" means only a typed refusal by orceld with a code other than `INTERNAL_ERROR`. Unconfirmed means everything else that is not a count: orceld did not start, the request could not be sent, no answer came within 30 seconds, orceld exited without one, the answer was not JSON, it was a success without a count, a failure without a code, or an `INTERNAL_ERROR`. An `orcel tunnel allow` cannot run between the revoke and the save: every `orcel tunnel` command holds the lifecycle lock for its whole run, its Windows Hello prompt included. A `remote.lease.create` sent to orceld some other way, with the same Windows Hello approval, is not ordered by that lock. A setup whose current runtime key cannot be read (any error but its absence) is refused before anything changes, because it could not be put back. The runtime key is written before the revoke, so a crash between the two leaves the new key beside the old setup; rerunning `orcel tunnel setup` fixes it, and the old route's leases are still reachable (`all_connections`, `connections_revoked_by_setup`, `revoke_each`, `revoke_reply`, `change_route`, `setup_failure`).
- **The relay stays core** (`crates/orcel-lifecycle/src/remote.rs` `check_relay_profile`, `apps/orcel-relay/src/authorization.ts`). `orcel remote pair --profile browser_full` (or any profile but `core`) is refused before anything runs, with a message that points at `orcel tunnel setup --profile browser_full`. The relay refuses a pairing offer that names any profile (`profile_unsupported`). Relay records, the relay edge's tool check (`edge.ts`), the device uplink (`device_uplink.ts`: `PairedConnection.toolSurfaceProfile` is `core`) and pairing (`remote_enrollment.ts`) name `core` only. No relay source mentions the browser profile, so no branch can be flipped silently, and a test pins that.
- **orceld defence in depth** (`crates/orcel-policy/src/remote_session.rs`). orceld does not trust a self-asserted profile. The strongest fact it observes is its own STRONG-created remote-session lease store, and every remote request must match a lease exactly: principal, remote connection, device, provider, client profile and profile. So a `browser_full` lease is built only when the local `orcel tunnel allow` proves the route is the tunnel's own. It sends the configured tunnel id, and the lease's principal, remote connection id and device id must be exactly what that id derives (`tunnel_browser_full_route`, the same derivation the lifecycle tunnel route uses), with provider `openai` and client profile `chatgpt-secure-mcp-tunnel-browser-full`. A relay route's device id is the device's own key identity and its connection id is the relay's, so it can never match a tunnel-derived lease, even if the relay or the uplink later forged the profile field. At dispatch, a `browser_full` context that does not name the tunnel's provider and client profile is refused before any lease is consulted. A core lease never names a tunnel id, and core leases and contexts are unchanged. A browser_full lease may name only `orcel.read` and `orcel.execute`, and a lease that names `orcel.write` or anything else is refused (`ob09_a_browser_full_lease_never_names_orcel_write`).
- **What this binding is, and is not.** The tunnel route ids are a plain SHA-256 hash of the tunnel id, and the tunnel id is not a secret (OpenAI's tunnel configuration knows it). There is no cryptographic binding between a request and the tunnel. The guarantees are:
  - local-process trust: only local code builds a remote context (`orcel-mcp-host` from the route it derives, and the device uplink, which hard-codes `core` for every relay connection), and orceld trusts what its local parent sends, as it does for every request;
  - the Windows Hello–gated `remote.lease.create`, which builds a browser_full lease only for the derived tunnel route, plus the exact match every remote request needs against that lease.

  A local process that could write orceld's stdin could also claim any context. That is outside this rule, as it is for every other remote check.
- **Session isolation is per tunnel host process, not per ChatGPT conversation.** Each tunnel host process has one remote kernel, whose `KernelClient.sessionId` (a server-side `randomUUID`) is the `client_session_id` behind its broker client and `client_ref`. If the tunnel client multiplexes several ChatGPT conversations over one host process, they share one broker namespace: each can name the others' browser sessions under the same remote-session lease. It is the same owner and the same tunnel, so this widens nothing across owners or routes.
- **Tool surface** (`apps/orcel-mcp/src/tool_contract.ts`, `server.ts`, `oauth_authorization.ts`). `REMOTE_BROWSER_FULL_TOOLS` (twelve tools) and their own scope matrix, separate from core's because four names are shared with local-only `browser_structured` tools. `allowedToolsFor` serves `browser_full` only on the tunnel transport, only for the providers in `REMOTE_BROWSER_FULL_PROVIDERS` (`openai`), and then only those tools; the relay transport is refused it for every provider. Every remote tool declares its exact OAuth scheme. Core's tools and scopes are unchanged and pinned.
- **Owner-only steps.** The tunnel setup and the remote-session lease (`orcel tunnel allow`, STRONG) run only at the PC. `orcel browser grant` is no part of the remote flow: it issues leases for local sessions only and refuses a remote client reference. `remote.*`, `browser.lease.*` and enrollment stay local-only in orceld, and no MCP tool reaches them.
