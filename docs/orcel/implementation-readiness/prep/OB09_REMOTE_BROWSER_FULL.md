# OB-09: remote `browser_full` for ChatGPT

**Status: part 1 (orceld gating) merged as #836 (a33e784e). Part 2 (the remote profile through the ChatGPT Secure MCP Tunnel only, and OAuth; section 6) implemented on `browser/ob09-remote-profile`, not merged. SG-000135 work packet OB-09, acceptance FA-D. Unit, cross-language and self-hosted relay tests only. UNVERIFIED (founder run): acceptance D needs a real ChatGPT run, and that needs the installed SG-000132 authority service and the founder.**

## 1. Decision

The founder delegated the open remote-coverage choice on 2026-11-22. Engineering chose the conservative option. The record is "founder-delegated, engineering-chosen (2026-11-22)". It is not a founder quote.

1. A remote `browser_full` Full Access lease is valid only when the installed SG-000132 authority service issued it and it is bound to the identified client (`client_ref`). The interim per-user full-control store never covers a remote caller.
2. The remote session must also hold the existing SG-000055 STRONG remote-session lease, created for the `browser_full` tool-surface profile.
3. High-impact actions still ask per action, exactly as locally: form submit or Enter in a form, submit, send, buy, publish or delete controls, uploads, payments and destructive actions. Anything not positively classified routine asks too.
4. The spec section 4.15 lift (a standing lease covering a remote caller) applies only to remote `browser_full` and only for the client named in the lease.

This lifts SG-000079's "no remote mapping" for `browser_full` only. `browser_structured` stays local-only. The host's `remote_browser_mapping_enabled()` (`crates/orcel-browser-host/src/exposure.rs`) stays `false`: it is SG-000079's marker for the closed grain's shapes, and the closed-grain qualification tests pin it.

## 2. Design

```
ChatGPT -> Secure MCP Tunnel set up for browser_full -> orcel-mcp-host (authenticated remote context; the relay serves core only)
  -> orceld profile gate: remote context names browser_full, shape is remote-safe
  -> SG-000055 remote-session lease (STRONG-created, browser_full profile, scopes, workstation, trust)
  -> broker as client "remote:<connection>:<principal>:<MCP session>", approvals stamped remote
  -> live browser: routine action under a service lease for this client_ref, or the Windows dialog
  -> receipt names caller {kind: remote, provider, device, connection}
```

**Remote-safe tools.** Each was decided from the specs:

| Tool | Shape | Remote scope | Why |
|---|---|---|---|
| `browser_session_create` | `create` | `orcel.execute` | Ephemeral profile only. Naming a persistent profile is refused, because it may be signed in to the owner's accounts. Visible mode still asks the owner first. |
| `browser_open`, `browser_click`, `browser_fill`, `browser_select`, `browser_tabs` | `open`, `click`, `fill`, `select`, `tabs` | `orcel.execute` | Each keeps its own SOFT approval, or a lease for routine actions only. Secret fields are refused, and a secret-looking or stored-secret value is never typed under a lease. |
| `browser_close` | `close` | `orcel.execute` | Ends the caller's own session. A window a person is using is never closed (OB-06). |
| `browser_snapshot`, `browser_verify`, `browser_extract`, `browser_screenshot`, `browser_task_status` | `snapshot`, `verify`, `extract`, `screenshot`, `status` | `orcel.read` | Reads of the caller's own session page. Screenshots mask secret fields, and URLs go through `agent_url`. |
| `browser_profiles`, `browser_profile_create`, `browser_profile_delete` | `profiles`, `profile_create`, `profile_delete` | local-only | These manage profiles that may hold the owner's sign-ins, and delete is destructive. |

No tool types into a secret field, handles a credential, or evaluates page script. `evaluate_in_page`, `credentials`, `payment_cards`, `solve_captcha` and `run` stay excluded. Uploads stay model-only and have no `browser_full` tool.

**Where the code is:**

- `crates/orcel-policy/src/remote_session.rs`. `browser_full` is now a second remote tool-surface profile (`REMOTE_PROFILES`). `required_browser_full_scopes` maps the twelve remote-safe shapes. `check_remote_dispatch` picks the scope table by the lease's own profile, so a `core` lease never covers a broker shape and a `browser_full` lease covers nothing else. `build_lease` accepts `browser_full`, under the same STRONG-gated local command. Its prompt names `profile=browser_full`. The core table and its cross-language test are unchanged.
- `crates/orceld/src/profile_gate.rs`. `REMOTE_BROWSER_FULL_SHAPES` lists the remote-safe shapes. A remote broker request passes the gate only when its authenticated remote context names `browser_full`, the shape is remote-safe, and `create` names no persistent profile. A local request whose MCP session id starts with `remote:` is refused, so it cannot pose as a remote client.
- `crates/orceld/src/sg000039_main.rs`. A remote broker request goes through `remote_session_gate` (the SG-000055 check, now shared with the core path) and then `handle_browser_full`. Its approval broker is the existing `OriginStamp`. Every prompt it raises is the owner's Windows dialog, marked remote with the provider, device and connection taken from the authenticated context. Nothing the remote caller sends can answer a prompt: the shapes take no approval or token field, and approvals come only from the local broker.
- `crates/orceld/src/browser_remote.rs`. `Caller` (local or remote). The broker client is `remote:<paired connection>:<principal>:<MCP session>`, so a remote client never reaches a local session or another remote client's session. The `client_ref` that a lease must name is derived from that client. `refuse_remote_profile` refuses persistent profiles a second time, after the gate.
- `crates/orceld/src/browser_lease.rs`. `FullAccess::for_remote_caller` marks a remote session. `LeaseSource::issuer` says who issues a source's leases. For a remote session, a lease from any issuer but the authority service, without the service's `al-` id, or naming another client or principal, is refused `lease_invalid` (CAPABILITY_DENIED, an existing code) at decide and again at confirm. Nothing is sent, and later actions ask. The routine and high-impact classification, the takeover gate, the epoch and revoke checks, and the service's audit-first `Authorize` are unchanged.
- `crates/orceld/src/browser_broker.rs` and `browser_receipts.rs`. Each session keeps its `Caller`. Its `session_start` event, every intent and every receipt carry `caller`: `{"kind":"local"}`, or `{"kind":"remote","provider","device","connection"}`. Each digest covers it.

- `crates/orceld/src/browser_broker.rs` (`needs_you_json`). In a remote caller's session, each Needs-you entry also carries `remote_caller` (provider and device, from the authenticated remote context, as the approval prompt's Origin line does). Its guidance says that a remote client drives the session, not someone at this PC, and that once the person completes the page (a sign-in included), that remote client acts in it as the signed-in account until the session ends. It never points at a persistent profile. The remote caller's reply carries nothing from the person's sign-in: only fixed words, the page id and the detector's closed signal names. Later replies show page URLs through `agent_url`, which masks query and fragment values after a sign-in.

**What is unchanged:** OB-06 takeover, OB-07 handoff (`HUMAN_VERIFICATION_REQUIRED`, which is refused before any lease is consulted, with the same failure code and handoff values), OB-07b sign-in and `agent_url`, the Shadow and Visible mode rules, and every local behaviour except the `remote:` prefix refusal. A local session's Needs-you entry is unchanged.

## 3. Threat model

**The interim-store exclusion is structural, not only a runtime check.** orceld has one real lease source, `authority_link::ServiceLeaseSource`. Its `issuer()` is `LeaseIssuer::AuthorityService`, and it admits a lease only after verifying the service's ECDSA signature with the public key the verified service reported. Every broker session's lease cache is built by `FullAccess::service_backed` (`live_dispatch.rs`, `start`), which wires in that source. `LeaseIssuer::InterimStore` is constructed only by the test source in `ob08_lease_tests.rs`, and no build of orceld issues or stores a browser lease. The runtime check in `FullAccess::refuse_for_remote` is defence in depth: it requires the service as issuer, the service's `al-` lease id, and a lease whose `client_ref` and principal both equal the remote session's own `client_ref`. That `client_ref` is derived from the remote broker client (paired connection, principal and MCP session), so a lease issued to any other client, local or remote, never matches. `check_browser_lease` checks the client binding again.

| Threat | Mitigation | Test |
|---|---|---|
| A remote caller with no STRONG remote-session lease drives the browser | The SG-000055 check runs after the profile gate and before anything else, and fails `REMOTE_SESSION_INACTIVE` | `ob09_remote_browser_full_without_a_strong_session_lease_is_refused` (policy), `ob09_remote_browser_full_without_a_strong_session_lease_never_reaches_dispatch` (orceld) |
| A `core` remote lease or token reaches browser tools, or a `browser_full` lease reaches files or processes | The scope table is chosen by the lease's profile, and lease and context profiles must match | `ob09_core_and_browser_full_leases_never_cover_each_other`, `ob09_a_browser_full_session_lease_covers_only_the_remote_safe_broker_shapes` |
| A remote caller uses or deletes a signed-in persistent profile | Gate, handler and dispatch each refuse it | `ob09_a_remote_session_never_names_a_persistent_profile`, `ob09_a_remote_caller_never_uses_a_persistent_profile`, `ob09_remote_browser_full_reaches_only_the_remote_safe_shapes` |
| An interim-store lease covers a remote caller | The remote session admits only `LeaseIssuer::AuthorityService` with an `al-` id; otherwise `lease_invalid` | `ob09_an_interim_store_lease_never_covers_a_remote_caller` |
| A lease issued to the local client, or to another remote client, covers this remote caller | `client_ref` and the principal are bound to connection, principal and MCP session | `ob09_a_service_lease_bound_to_another_client_is_refused_for_remote`, `ob09_a_remote_client_is_bound_to_its_connection_and_principal` |
| A remote caller submits, buys, publishes or deletes without the owner | High-impact and unknown actions are never covered and ask on the Windows dialog, marked remote | `ob09_high_impact_and_unclassified_remote_actions_always_ask`, `a_remote_requests_approvals_are_marked_remote` (existing) |
| A local process poses as a remote client to reach its sessions | Local ids with the `remote:` prefix are refused | `ob09_local_browser_full_is_unchanged`, `ob09_local_callers_are_unchanged` |
| Receipts cannot tell a remote action from a local one | `caller` is in every intent, receipt and session start, and digest-covered | `ob09_receipts_carry_the_remote_origin`, `ob09_receipts_name_the_remote_origin` |
| The person signs in for a session without knowing that a remote client will then drive it, or the remote reply leaks something from that sign-in | Remote Needs-you entries name the remote provider and device and say that the remote client then acts in the page; the entries hold fixed words only; URLs are masked after a sign-in | `ob09_a_remote_sessions_handoff_names_the_remote_client_and_carries_nothing_from_the_sign_in` |
| Routine remote actions under the right lease still prompt every time (FA-D usability) | They are covered as locally, after the service's `Authorize` | `ob09_routine_remote_actions_under_this_clients_service_lease_are_covered` |

## 4. Residuals

- **UNVERIFIED (founder run).** No real ChatGPT run has happened. It needs the installed authority service and the founder at the PC for every owner step: `orcel tunnel setup --profile browser_full`, a STRONG remote-session lease from `orcel tunnel allow`, a lease from `orcel browser grant` for the remote session's `client_ref` (optional; without it every consequential action asks), and the dialogs. ChatGPT must also allow write tools in the founder's plan, and Orcel cannot turn them on.
- The remote-session lease lasts at most 15 minutes (SG-000055), and a reconnect does not extend it. A long remote task needs a new lease.
- No live-browser run was made with a remote context. The Windows `live-browser-dev` build compiles and passes clippy, and the remote path reuses the same live code as the local one.
- The OAuth scopes are reused (`orcel.read` for reads, `orcel.execute` for actions). There is no browser-only scope. The separation comes from the `browser_full` tool-surface profile, which the tunnel setup or the pairing and the STRONG lease bind. A dedicated scope would need SG-000054 vocabulary changes in the relay and the OAuth server.
- **Tunnel only** (engineering-chosen 2026-11-22 under the founder's delegation, matching the founder's directive of ChatGPT through the Secure MCP Tunnel). The relay registers every OAuth client as provider `generic` and cannot tell ChatGPT from another client, so the relay never serves `browser_full`: `orcel remote pair --profile browser_full` is refused with a message that points at the tunnel, the relay refuses a pairing offer that names any profile, the relay edge and the device uplink check tools against `core` only, and a relay paired connection holds `core` only. A remote ChatGPT session that uses the relay instead of the tunnel gets the core profile.
- High-impact signals are still the OB-08 heuristics (open choice 4). An action that is wrongly classified routine would be covered. The host's GET-only binding while covered actions run still blocks a non-GET request.
- A per-request read mode asks for each remote read, which makes snapshots slow. A session read mode is the owner's choice at lease creation.

## 5. Next steps (part 2, the MCP remote profile)

Done in part 2 (section 6):

- **`client_session_id` for a remote caller is the server-assigned MCP session id, never chosen by the caller.** The remote broker client and the `client_ref` that a lease must name are built from it (with the paired connection and the principal). The MCP edge sets it from `KernelClient.sessionId`, a server-side `randomUUID` per remote kernel, and never takes it from a tool argument, a header or anything the remote caller sends. A tool argument naming one is refused by the tool's strict schema before anything reaches orceld. Pinned by `ob09: a remote kernel's client_session_id is its own server-side randomUUID and no input changes it` and `ob09: a browser_full tunnel serves only the remote browser tools and every request carries the remote context, profile browser_full, and the server's own session id`.
- The tunnel route and the remote context carry `browser_full`, chosen locally by the owner (`orcel tunnel setup --profile browser_full`). Relay pairing, the relay route, the relay edge and the device uplink stay `core` only (tunnel-only rule, section 4).
- The remote tool contract has the twelve remote-safe tools with the scopes of `required_browser_full_scopes`, and a cross-language test pins it. The OAuth ceilings have a `browser_full` profile limited to those tools. `TOOL_CONTRACT.md` is regenerated.

## 6. Part 2: the remote profile through the ChatGPT Secure MCP Tunnel

**Tunnel only, one profile per tunnel, chosen by the owner on the PC** (engineering-chosen 2026-11-22 under the founder's delegation). A ChatGPT Secure MCP Tunnel serves exactly one remote profile: `core` (the default, unchanged) or `browser_full`. The relay serves `core` only. Nothing remote can choose, enroll or widen a profile.

- **Tunnel** (`crates/orcel-lifecycle/src/tunnel_route.rs`, `config.rs`, `commands.rs`, `mcp_host.rs`). `orcel tunnel setup --profile browser_full` records `profile` in the tunnel settings (`core` is the default and is never written). `route_for` derives a `browser_full` route with its own remote connection id and client profile (`chatgpt-secure-mcp-tunnel-browser-full`) and the scope ceiling `orcel.read orcel.execute`, never `orcel.write`. So a core lease never covers it, and `orcel tunnel allow` (STRONG) leases its own connection. `orcel-mcp-host` passes that route down. The core route and its ids are unchanged and pinned.
- **The relay stays core** (`crates/orcel-lifecycle/src/remote.rs` `check_relay_profile`, `apps/orcel-relay/src/authorization.ts`). `orcel remote pair --profile browser_full` (or any profile but `core`) is refused before anything runs, with a message that points at `orcel tunnel setup --profile browser_full`. The relay refuses a pairing offer that names any profile (`profile_unsupported`). Relay records, the relay edge's tool check (`edge.ts`), the device uplink (`device_uplink.ts`: `PairedConnection.toolSurfaceProfile` is `core`) and pairing (`remote_enrollment.ts`) name `core` only. No relay source mentions the browser profile, so no branch can be flipped silently, and a test pins that.
- **orceld defence in depth** (`crates/orcel-policy/src/remote_session.rs`). orceld does not trust a self-asserted profile. The strongest fact it observes is its own STRONG-created remote-session lease store, and every remote request must match a lease exactly: principal, remote connection, device, provider, client profile and profile. So a `browser_full` lease is built only when the local `orcel tunnel allow` proves the route is the tunnel's own. It sends the configured tunnel id, and the lease's principal, remote connection id and device id must be exactly what that id derives (`tunnel_browser_full_route`, the same derivation the lifecycle tunnel route uses), with provider `openai` and client profile `chatgpt-secure-mcp-tunnel-browser-full`. A relay route's device id is the device's own key identity and its connection id is the relay's, so it can never match a tunnel-derived lease, even if the relay or the uplink later forged the profile field. At dispatch, a `browser_full` context that does not name the tunnel's provider and client profile is refused before any lease is consulted. A core lease never names a tunnel id, and core leases and contexts are unchanged. A browser_full lease may name only `orcel.read` and `orcel.execute`, and a lease that names `orcel.write` or anything else is refused (`ob09_a_browser_full_lease_never_names_orcel_write`).
- **What this binding is, and is not.** The tunnel route ids are a plain SHA-256 hash of the tunnel id, and the tunnel id is not a secret (OpenAI's tunnel configuration knows it). There is no cryptographic binding between a request and the tunnel. The guarantees are:
  - local-process trust: only local code builds a remote context (`orcel-mcp-host` from the route it derives, and the device uplink, which hard-codes `core` for every relay connection), and orceld trusts what its local parent sends, as it does for every request;
  - the Windows Hello–gated `remote.lease.create`, which builds a browser_full lease only for the derived tunnel route, plus the exact match every remote request needs against that lease.

  A local process that could write orceld's stdin could also claim any context. That is outside this rule, as it is for every other remote check.
- **Session isolation is per tunnel host process, not per ChatGPT conversation.** Each tunnel host process has one remote kernel, whose `KernelClient.sessionId` (a server-side `randomUUID`) is the `client_session_id` behind its broker client and `client_ref`. If the tunnel client multiplexes several ChatGPT conversations over one host process, they share one broker namespace: each can name the others' browser sessions and is covered by the same Full Access lease. It is the same owner and the same tunnel, so this widens nothing across owners or routes, but a lease issued for that client covers every conversation on that tunnel host.
- **Tool surface** (`apps/orcel-mcp/src/tool_contract.ts`, `server.ts`, `oauth_authorization.ts`). `REMOTE_BROWSER_FULL_TOOLS` (twelve tools) and their own scope matrix, separate from core's because four names are shared with local-only `browser_structured` tools. `allowedToolsFor` serves `browser_full` only on the tunnel transport, only for the providers in `REMOTE_BROWSER_FULL_PROVIDERS` (`openai`), and then only those tools; the relay transport is refused it for every provider. Every remote tool declares its exact OAuth scheme. Core's tools and scopes are unchanged and pinned.
- **Owner-only steps.** The tunnel setup, the remote-session lease (`orcel tunnel allow`, STRONG), and `orcel browser grant` (service, Windows Hello) all run only at the PC. `remote.*`, `browser.lease.*` and enrollment stay local-only in orceld, and no MCP tool reaches them.

| Threat (part 2) | Mitigation | Test |
|---|---|---|
| A remote route gets core and browser tools at once, or switches silently | One profile per route; the `browser_full` tunnel route has its own connection id; the lease's profile picks orceld's scope table | `ob09_a_browser_full_tunnel_route_is_separate_and_admits_only_broker_shapes`, `ob09: core is unchanged and the two remote profiles never overlap` |
| Something remote enrolls a route for `browser_full` | Only the owner's local `orcel tunnel setup --profile browser_full` sets it; relay pairing refuses any profile but `core`, and the relay refuses an offer that names one | `ob09_relay_pairing_refuses_browser_full_and_points_at_the_tunnel`, `SG-000135 OB-09: the relay serves the core profile only and never a browser tool` |
| A relay-shaped `browser_full` context reaches orceld (a relay or uplink that later forges the profile) | orceld builds a browser_full lease only for the route the configured tunnel id derives, and every remote request must match a lease exactly; a browser_full context without the tunnel's provider and client profile is refused first | `ob09_only_the_tunnels_own_browser_full_route_gets_a_lease_or_dispatches`, `ob09_a_browser_full_tunnel_route_is_separate_and_admits_only_broker_shapes` |
| The relay serves a browser tool (now, or after a silent flip) | No relay source names the profile; the relay edge and uplink check `core` only; the relay transport is refused `browser_full` | `SG-000135 OB-09: the relay serves the core profile only and never a browser tool`, `ob09: the relay never serves browser_full: its server, its uplink check and its pairing record stay core` |
| A remote caller picks another client's session id, and so its sessions and lease | `client_session_id` is the server-side `randomUUID`; the tools' strict schemas refuse the field | `ob09: a remote kernel's client_session_id is its own server-side randomUUID and no input changes it`, `ob09: a browser_full tunnel serves only the remote browser tools ...` |
| A browser_full tunnel reaches a core tool (files, processes) | The served list denies it; orceld's browser_full lease covers no core shape | `ob09: a browser_full tunnel serves only the remote browser tools and every request carries the remote context, profile browser_full, and the server's own session id`, `ob09_a_browser_full_tunnel_route_is_separate_and_admits_only_broker_shapes` |

| A tunnel config with another profile starts | Config validation refuses any profile but `core` or `browser_full` | `ob09_the_tunnel_profile_defaults_to_core_and_only_core_or_browser_full_load` |
