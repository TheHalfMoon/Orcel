## The existing fixture is not a starting point

`tests/native-fixtures/apps/cross-platform/tauri/` is Cua's native test harness, imported unmodified under XP-08 (`0c090c41`) and built by no CI job. It is consistent with "no Vite, no Tauri CLI, no React": it builds with plain `cargo build --release --features custom-protocol`, and its `package.json` only wraps cargo. That is useful evidence that a CLI-free Tauri 2 build works. It must not be copied as the Control Room base, because it conflicts with this grain's authority boundary:

- `"csp": null`: no Content Security Policy at all.
- It starts a `tiny_http` server on `127.0.0.1:0` and loads `WebviewUrl::External("http://127.0.0.1:<port>/")`. That is a listener, and content loaded over HTTP rather than embedded assets.
- `js_init_script` injects an environment variable's value into every page.
- `tauri = "2"` and `tauri-build = "2"` are unpinned, there is no `Cargo.lock`, and default features (including dynamic ACL and compression) are on.
- No capability files, so no command allowlist is expressed.
- `"$schema": "https://schema.tauri.app/config/2"` is a remote URL (editor-only, harmless, but the Control Room config will not carry it).

The fixture stays a cua-driver test target and is not changed by this grain.

## Recommended scope: Windows first

**Recommendation: native evidence on Windows only in this grain; macOS and Linux get compile-and-unit-test CI legs as an optional last slice, under their own download approval; their native qualification is a successor grain.**

Why:

1. **The founder's evidence machine is Windows.** Every slice needs native evidence. Windows is where orceld's app API, the founder's PC and the WPF baseline all are.
2. **CR-04's parity gate is a Windows comparison.** WPF exists only on Windows, so the measurements that decide retirement are Windows measurements.
3. **WebView2 is the smallest supply-chain step.** It is an operating-system component on Windows 11; nothing is installed. Linux needs WebKitGTK 4.1 development packages from apt (a further download) and pulls gtk3-rs crates that RustSec lists as unmaintained. macOS builds are unsigned (FD-05), and Gatekeeper and screen-reader checks need the founder's Mac.
4. **The renderer boundary differs per OS** (see "Authority boundary"). On Windows the WebView2 renderer cannot open orceld's pipe. On Linux, whether a WebKitGTK web process can reach the app API socket depends on WebKitGTK's own sandbox, which must be shown before Linux ships, for the same reason `task.stop`'s exception carries an SG-000115 gate.
5. **It keeps the grain small.** CR-03 estimates 5 to 8 days for three OSes with React reuse. Without React reuse and with three OSes, the honest estimate grows. Windows first keeps each slice reviewable.

The cost: the "same window on three OSes" outcome of CR-03 is not delivered by this grain alone. The Rust bridge and the front end are written OS-neutral from the start (the Unix endpoint checks are in slice A1), so the successor is mostly CI, packaging and native checks.

## Authority boundary

**orceld remains the sole authority.** The Control Room is a viewer. Authority delta: none.

**What it reads, and how.** The Tauri Rust process (not the web view) is the only app API client. It opens this user's endpoint exactly as `ORCEL_APP_API_1.md` section 7 asks:

- **Windows:** `\\.\pipe\orcel-<user SID>-app`, opened with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`. Before sending a byte it reads `GetNamedPipeServerProcessId`, opens that process, and requires its token user to equal its own and its integrity to be Medium or above (as the WPF preview does). orceld's `describe_holder` and `token_user` (`crates/orceld/src/app_api.rs`) already implement the identification-only open and the account comparison, and slice A1 lifts them into a shared crate rather than writing them again.
- **macOS and Linux:** the socket under the user's runtime directory, with the same no-follow checks as the TypeScript client (directory owned by this uid with no group or other access; socket is a socket owned by this uid).
- **Methods:** `status.get`, `capabilities.get` and `events.subscribe` only, as a closed Rust enum, so an unlisted name cannot be serialized, let alone sent. `task.list` and `task.get` are read-only and served, but are not in the first allowlist (question 5). `task.stop`, `approval.history`, `clients.list` and every name orceld answers `UNKNOWN_METHOD` are absent.
- **Frames:** at most 64 KiB per frame, newline included; epoch-aware cursors; a gap is rejected before the cursor moves; a new epoch clears the timeline (the protocol's rules, reused from the headless client's reducer in the front end and mirrored in Rust).

**What the web view can call.** Three Tauri commands and nothing else:

| Command | Argument | Answer |
|---|---|---|
| `app_status` | none | the `status.get` result, validated |
| `app_capabilities` | none | the `capabilities.get` result, validated |
| `app_events` | a `tauri::ipc::Channel` and an optional `{after_seq, epoch}` | streams validated events and snapshots; ends on window close |

CR-03 step 2 proposed one generic `app_api_call` with a name allowlist. Three typed commands are recommended instead: an argument cannot carry a method name, so there is no string to smuggle. The names are listed once, in `build.rs` (`tauri_build::Attributes::new().app_manifest(AppManifest::new().commands(&[...]))`), so each command needs an explicit permission, and the `invoke_handler` registers exactly these three. A test compares the two lists.

**Capabilities (Tauri ACL).** One capability file, for the window labelled `main` only, granting only the three generated `allow-app-*` permissions. No `core:default`, no `core:window:*`, `core:webview:*`, `core:event:*`, `core:path:*` or `core:app:*` permission, no `remote` section (no remote URL may call IPC), no platform-wide wildcard. No plugin is registered: no shell, fs, http, dialog, opener, process, updater, clipboard, notification, global-shortcut, deep-link or store plugin. CI fails if any `tauri-plugin-*` crate appears in the resolved graph (a `cargo tree` check like the native host's QuickJS check).

**Content Security Policy.** Set in `tauri.conf.json` `app.security.csp`, so Tauri adds its own script hashes and nonces at build time:

```
default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src ipc: http://ipc.localhost; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'
```

No `'unsafe-inline'`, `'unsafe-eval'`, `'wasm-unsafe-eval'`, `ws:`, `wss:`, `http:` or `https:` source. `dangerousDisableAssetCspModification` stays false. Slice A2 confirms the IPC origin list on WebView2 empirically and narrows it if Tauri needs less.

**No remote content.**

- Assets are embedded at compile time (`custom-protocol` feature, `frontendDist` pointing at the compiled front end). There is no `devUrl`, no dev server and no listener of any kind.
- The window is built with an `on_navigation` handler that allows only Tauri's own asset origin (`tauri://localhost` or `http://tauri.localhost` on Windows) and refuses everything else, and new windows are refused.
- `dragDropEnabled: false`, so a dropped file cannot navigate the view.
- Devtools are off: the `devtools` feature is not enabled, and release-profile builds cannot open them.
- `withGlobalTauri: true` exposes `window.__TAURI__.core.invoke` so no `@tauri-apps/api` npm package is needed. The page is the only content the view ever loads.

**Untrusted strings.** Events can carry planner titles, workspace paths and other text orceld did not write. The front end renders every field with `textContent`, never `innerHTML`, `insertAdjacentHTML`, `document.write`, `eval` or `Function`; a static check in the front end's tests fails on any of them. Control and bidi characters are replaced, as the WPF preview does.

**Approvals are never actionable.** A pending approval is shown as "waiting for approval on this device"; the decision stays with the OS prompt. No button, link or keyboard path answers, cancels or mints an approval.

**The renderer cannot reach orceld.** On Windows, the WebView2 renderer runs in Chromium's sandbox below Medium integrity, and the pipe's `ME` mandatory label refuses it, so page script, even a compromised renderer, can reach orceld only through the three commands. This matters beyond reads: `task.stop`'s exception to the first-party code rule (`ORCEL_APP_API_1.md` section 2) rests on no confined process reaching the endpoint. Slice A5 records native evidence for Windows. On Linux this must be shown for WebKitGTK's web process before any Linux build ships (successor).

**Environment overrides.** WebView2 honours `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER`, `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, `WEBVIEW2_USER_DATA_FOLDER` and `WEBVIEW2_RELEASE_CHANNEL_PREFERENCE`, and the same through policy registry keys. An argument such as `--remote-debugging-port` would open a listener. The Rust `main` refuses to start, with a stated reason, when any `WEBVIEW2_*` variable is set, and passes no additional browser arguments. A same-user process can still change the user's environment or registry; that is the same residual as squatting the pipe (below), recorded rather than solved.

**WebView2 user data.** WebView2 writes a user data folder (by default under `%LOCALAPPDATA%\<identifier>\EBWebView`). It holds no Orcel state, only the view's cache. The draft sets an explicit folder under the Control Room's own per-user directory, outside orceld's state root, and `orcel uninstall --purge-data` is not extended in this grain (recorded as a known limit).

**Accepted residuals (same as the WPF preview).** The pipe name is predictable: another same-user process at Medium integrity could serve it first and show invented state. Nothing it shows can act, because the Control Room sends nothing that acts.

## Security review plan

- **Every slice:** a fresh-context security judge on the exact head; Jev semantic review; Alibaba Open Code Review in delegation mode with manual review of excluded files; exact-head CI. d1-local is advisory only and never clears a gate.
- **Checklist for the judge:**
  1. CSP string exactly as recorded; no unsafe source; Tauri's injected hashes and nonces only.
  2. Capability file: one window, three permissions, no `remote`, no core defaults; `invoke_handler` and the manifest name the same three commands.
  3. No plugin, listener, `devUrl`, updater, bundler output, `macOSPrivateApi` or `dangerous*` setting; devtools absent from release-profile builds.
  4. Navigation and new-window refusal covers every scheme; drag-drop off.
  5. The Rust client: identification-only open, server token user and integrity checked before the first write, closed method enum, frame cap, no `task.stop`.
  6. Front end: text only, no HTML sinks, no approval affordance.
  7. `WEBVIEW2_*` refusal; no additional browser arguments.
  8. Dependency graph: the resolved lock reviewed against this packet's table; licenses; RustSec advisories, each unmaintained or unsound one recorded with why it is reachable or not.
- **Closeout:** a whole-grain judge over A1 to A6 against the invariants in the draft spec.

## Release-build stance
