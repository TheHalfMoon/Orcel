## The existing fixture is not a starting point

`tests/native-fixtures/apps/cross-platform/tauri/` is Cua's native test harness, imported unmodified under XP-08 (`0c090c41`) and built by no CI job. It is consistent with "no Vite, no Tauri CLI, no React": it builds with plain `cargo build --release --features custom-protocol`, and its `package.json` only wraps cargo. That is useful evidence that a CLI-free Tauri 2 build works. It must not be copied as the Control Room base, because it conflicts with this grain's authority boundary:

- `"csp": null`: no Content Security Policy at all.
- It starts a `tiny_http` server on `127.0.0.1:0` and loads `WebviewUrl::External("http://127.0.0.1:<port>/")`. That is a listener, and content loaded over HTTP rather than embedded assets.
- `js_init_script` injects an environment variable's value into every page.
- `tauri = "2"` and `tauri-build = "2"` are unpinned, there is no `Cargo.lock`, and default features (including dynamic ACL and compression) are on.
- No capability files, so no command allowlist is expressed.
- `"$schema": "https://schema.tauri.app/config/2"` is a remote URL (editor-only, harmless, but the Control Room config will not carry it).

The fixture stays a cua-driver test target and is not changed by this grain.

## Scope (decided): Windows only

**Founder decision 2:** Windows first; macOS and Linux later in independently qualified stages. This grain therefore:

- **Qualifies Windows only** (WebView2), with native Windows evidence on every slice that runs the window.
- **Keeps Linux out entirely.** No Linux leg for `src-tauri`, no WebKitGTK packages (decision 4 allows them only on disposable GitHub Actions Linux runners once Linux build qualification begins, in its own stage, and never on the founder's machines).
- **Allows one optional extra: a macOS compile check** (slice A6): `cargo build --locked` and the configuration and unit tests of `src-tauri` on `macos-latest`, never launching the window. Why Windows first (the reasons the founder accepted):

1. The founder's PC, orceld's app API evidence and the WPF baseline are on Windows.
2. CR-04's parity gate is a Windows comparison.
3. WebView2 is an operating-system component on Windows 11; nothing is installed.
4. On Windows the WebView2 renderer cannot open orceld's pipe (see "Authority boundary"); on Linux, whether WebKitGTK's web process can reach the app API socket must be shown first, for the same reason `task.stop`'s exception carries an SG-000115 gate.

The Rust bridge and the front end are written OS-neutral (the Unix endpoint checks are in slice A1), so the later macOS and Linux stages are mostly CI, packaging and native checks.

## Authority boundary

**orceld remains the sole security and authorization authority.** The Control Room is a viewer. Authority delta: none. The UI performs no browser, filesystem, shell or privileged action, directly or through a plugin.

**What it reads, and how.** The Tauri Rust process (not the web view) is the only app API client. It opens this user's endpoint exactly as `ORCEL_APP_API_1.md` section 7 asks:

- **Windows:** `\\.\pipe\orcel-<user SID>-app`, opened with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`. Before sending a byte it reads `GetNamedPipeServerProcessId`, opens that process, and requires its token user to equal its own and its integrity to be Medium or above (as the WPF preview does). orceld's `describe_holder` and `token_user` (`crates/orceld/src/app_api.rs`) already implement the identification-only open and the account comparison, and slice A1 lifts them into a shared crate rather than writing them again.
- **macOS and Linux (code only, not qualified here):** the socket under the user's runtime directory, with the same no-follow checks as the TypeScript client.
- **Methods:** `status.get`, `capabilities.get`, `events.subscribe`, `task.list` and `task.get` (decision 5), as a closed Rust enum, so an unlisted name cannot be serialized, let alone sent. `task.stop`, `approval.history`, `clients.list` and every name orceld answers `UNKNOWN_METHOD` are absent.
- **Frames:** at most 64 KiB per frame, newline included; epoch-aware cursors; a gap is rejected before the cursor moves; a new epoch clears the timeline.

**Report tasks: the decision 5 bound.** `task.list` and `task.get` are read-only and orceld serves them today. orceld already reports paths workspace-relative (`report_task.rs`, `destination_of`), and records hold paths, sizes, hashes, states and step outcomes, never file content. The Control Room does not rely on that alone. Its Rust side re-shapes every answer before the web view sees it:

- **Field allowlist.** Kept: `task_id`, `kind`, `state`, `owner`, `workspace_id`, `created_at_ms`, `updated_at_ms`, `title` (planner-supplied, capped at 120 characters, shown labelled as planner-supplied), `folder`, `sources[].path`, `sources[].sha256`, `sources[].bytes`, `proposal` and `report` as `{name, destination, sha256, bytes}`, `steps[]` as `{step_id, kind, outcome, at_ms}`, and from `check` only `checker`, `passed`, `destination`, `bytes`, `sha256`, `sources_unchanged`, `figures_confirmed` and `checked_at_ms`. Every other field, including any field orceld adds later, is dropped.
- **Path rule.** A path is shown only if it is workspace-relative: not empty, no drive letter, no leading `/` or `\`, no UNC or `\\?\` prefix, no `..` or `.` segment, no NUL or control character, at most 1024 bytes. A path that fails is replaced by "path withheld" and counted; it is never shown, opened or resolved. The Control Room never joins a path to a workspace root, never touches the file system for it, and offers no "open file" or "reveal" action.
- **Hashes** must be 64 lowercase hex characters, or are withheld the same way.
- **Never shown:** report content, source content, secrets, and any location outside a workspace.

**What the web view can call.** Five Tauri commands and nothing else:

| Command | Argument | Answer |
|---|---|---|
| `app_status` | none | the `status.get` result, validated |
| `app_capabilities` | none | the `capabilities.get` result, validated |
| `app_events` | a `tauri::ipc::Channel` and an optional `{after_seq, epoch}` | streams validated events and snapshots; ends on window close |
| `app_tasks` | none | `task.list`, re-shaped by the bound above |
| `app_task` | `task_id` (string, at most 128 bytes, `[A-Za-z0-9_-]` only) | `task.get`, re-shaped by the bound above |

CR-03 step 2 proposed one generic `app_api_call` with a name allowlist. Typed commands are used instead: no argument can carry a method name. The names are listed once, in `build.rs` (`tauri_build::Attributes::new().app_manifest(AppManifest::new().commands(&[...]))`), so each command needs an explicit permission, and the `invoke_handler` registers exactly these five. A test compares the two lists.

**Capabilities (Tauri ACL).** One capability file, for the window labelled `main` only, granting only the five generated `allow-app-*` permissions. No `core:default`, no `core:window:*`, `core:webview:*`, `core:event:*`, `core:path:*` or `core:app:*` permission, no `remote` section, no platform-wide wildcard. No plugin is registered: no shell, fs, http, dialog, opener, process, updater, clipboard, notification, global-shortcut, deep-link or store plugin. CI fails if any `tauri-plugin-*` crate appears in the resolved graph (a `cargo tree` check like the native host's QuickJS check).

**Content Security Policy.** Set in `tauri.conf.json` `app.security.csp`, so Tauri adds its own script hashes and nonces at build time:

```
default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src ipc: http://ipc.localhost; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'
```

No `'unsafe-inline'`, `'unsafe-eval'`, `'wasm-unsafe-eval'`, `ws:`, `wss:`, `http:` or `https:` source. `dangerousDisableAssetCspModification` stays false. Slice A2 confirms the IPC origin list on WebView2 empirically and narrows it if Tauri needs less.

**No remote content.**

- Assets are embedded at compile time (`custom-protocol` feature, `frontendDist` pointing at the compiled front end). There is no `devUrl`, no dev server and no listener of any kind.
- The window is built with an `on_navigation` handler that allows only Tauri's own asset origin (`tauri://localhost` or `http://tauri.localhost` on Windows) and refuses everything else, and new windows are refused.
- `dragDropEnabled: false`, so a dropped file cannot navigate the view.
- Devtools are off: the `devtools` feature is not enabled, and release-profile builds cannot open them.
- `withGlobalTauri: true` exposes `window.__TAURI__.core.invoke` so no `@tauri-apps/api` npm package is needed. The page is the only content the view ever loads.

**Untrusted strings.** Events and tasks carry planner titles, workspace paths and other text orceld did not write. The front end renders every field with `textContent`, never `innerHTML`, `insertAdjacentHTML`, `document.write`, `eval` or `Function`; a static check in the front end's tests fails on any of them. Control and bidi characters are replaced, as the WPF preview does.

**Approvals are never actionable, and never bypassed.** A pending approval is shown as "waiting for approval on this device"; the decision stays with the OS prompt. No button, link or keyboard path answers, cancels, dismisses or mints an approval, and nothing in this grain scripts or suppresses a human approval prompt.

**The renderer cannot reach orceld.** On Windows, the WebView2 renderer runs in Chromium's sandbox below Medium integrity, and the pipe's `ME` mandatory label refuses it, so page script, even a compromised renderer, can reach orceld only through the five commands. This matters beyond reads: `task.stop`'s exception to the first-party code rule (`ORCEL_APP_API_1.md` section 2) rests on no confined process reaching the endpoint. Slice A5 records native evidence for Windows.

**Environment overrides.** WebView2 honours `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER`, `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, `WEBVIEW2_USER_DATA_FOLDER` and `WEBVIEW2_RELEASE_CHANNEL_PREFERENCE`, and the same through policy registry keys. An argument such as `--remote-debugging-port` would open a listener. The Rust `main` refuses to start, with a stated reason, when any `WEBVIEW2_*` variable is set, and passes no additional browser arguments. A same-user process can still change the user's environment or registry; that is the same residual as squatting the pipe (below), recorded rather than solved.

**WebView2 user data.** WebView2 writes a user data folder (by default under `%LOCALAPPDATA%\<identifier>\EBWebView`). It holds no Orcel state, only the view's cache. The draft sets an explicit folder under the Control Room's own per-user directory, outside orceld's state root, and `orcel uninstall --purge-data` is not extended in this grain (recorded as a known limit).

**Accepted residuals (same as the WPF preview).** The pipe name is predictable: another same-user process at Medium integrity could serve it first and show invented state. Nothing it shows can act, because the Control Room sends nothing that acts.
