# macOS M0 readiness: the audit and plan for macOS as Orcel's second platform

**Status: PREPARATION ONLY (M0).** This packet changes no code, activates no grain, grants no authority and claims no macOS release. It records what current `main` already does on macOS, what it only compiles, what it refuses, and what must happen before macOS can claim feature and security parity with Windows. Anything this audit could not prove from a file, a test or a CI job is marked **UNVERIFIED**. Unsupported capabilities stay fail-closed. Windows SG-000119 work continues first, and nothing proposed here touches a Windows code path without a Windows-pinned non-regression test.

## 1. Executive summary

macOS is much further along than "second platform" suggests, but it is not a product. The kernel and most security primitives already run natively on macOS and are exercised on hosted macOS CI. What is missing is the product layer around them, and four authority gates that are deliberately Windows-only today.

**Already native on macOS, with native tests:**
- `orceld` binds its app API as a 0600 Unix socket under the per-user `confstr(_CS_DARWIN_USER_TEMP_DIR)` directory, and admits a peer only through `getpeereid` plus the `LOCAL_PEERTOKEN` audit token bound to the process's unique id (`crates/orcel-platform/src/peer.rs:340-476`). CI proves another user is refused (`ci.yml:263-267`).
- Approvals use a system-drawn `CFUserNotification` (SOFT) and LocalAuthentication `LAContext` (STRONG). Both were qualified on the founder's Mac (Apple M2, macOS 26.6.2) and fail closed headless in CI (`SECURITY_INTEGRATION.md:77`, `ci.yml:233-242`).
- Secrets go to the user's Keychain with UI disabled and no plaintext fallback (`crates/orceld/src/secret_store.rs:1082-1191`, `ci.yml:281-301`).
- The contained tier runs untrusted helpers under a deny-by-default Seatbelt profile (`apps/orcel-contain/src/macos.rs`, `ci.yml:697-737`).
- Clipboard read and write work against the real pasteboard (`ci.yml:223-227`).
- The native host (vendored Cua `platform-macos`) observes the desktop through the Accessibility API. Observation and semantic actions passed on a real Mac (`SECURITY_INTEGRATION.md:96`, `:147`).
- An unsigned development tarball is built, checksummed and run in CI (`ci.yml:1682-1761`).

**Deliberately refused or Windows-only today (fail-closed):**
- The `orcel` CLI's install, start, stop, status, supervise and `mcp stdio` refuse or are wired to `orceld.exe` (`crates/orcel-lifecycle/src/lifecycle.rs:565-593`, `crates/orcel-lifecycle/src/mcp.rs:54`). Since MAC-M1-02 (#834) the `orceld` file name and the presence wording come from per-OS helpers (`crates/orcel-lifecycle/src/per_os.rs`), but these commands still verify the Windows install first, so they still refuse on macOS.
- The Full User desktop lease, which gates every desktop action and shell, is Windows-only (`crates/orcel-policy/src/full_control_store.rs:203-208`, `:644-649`), so no desktop action reaches the native host through `orceld` on macOS (`SECURITY_INTEGRATION.md:136`).
- Browser engine launch is refused on macOS before discovery (`crates/orcel-browser-host/src/host.rs:498-508`); SG-000115 is not activated.
- Network fetch has no native transport off Windows (`crates/orcel-provider-network/src/lib.rs:170`).
- No macOS release, SBOM, provenance or install/remove flow exists (`.github/workflows/release.yml` builds only Windows and Linux).

**Matrix summary (section 2, 20 capabilities):** 7 IMPLEMENTED (native code and native tests, but no macOS release security review and no parity claim), 10 PARTIAL, 1 FAIL-CLOSED, 2 NOT STARTED. **Parity is claimed for none.**

**Recommended minimum macOS version: macOS 15 Sequoia, Apple Silicon (arm64) only, for M1 to M5** (section 4). The floor rests on the capture-consent logic being written for macOS 15, on every native result so far coming from macOS 26.6.2, and on the backlog's install matrix naming 15 and 26; the vendored capture path needs at least macOS 14 (ext). Intel is deferred.

**Offline compile check (this audit):** `cargo check --offline --workspace --target aarch64-apple-darwin` on this Windows PC finished with exit 0 in 4 min 36 s (the target was already installed). That proves only that the root workspace type-checks for Apple Silicon; it does not link, run, or cover `apps/orcel-native-host` and `apps/orcel-contain`, which are separate workspaces. `x86_64-apple-darwin` is **not installed** here, so no Intel check was run (installing it is a download; see founder approvals).

**Findings that need action before macOS authority grows** (none is reachable in a release build today):
1. `crates/orcel-provider-browser/src/lib.rs:3333-3351`: `path_key` rewrites `/` to `\` on every OS and `path_is_within` compares string prefixes. On Unix `\` is a legal file name character, so a sibling directory literally named `ws\x` keys as if it were inside `ws`. The browser is refused on macOS today, so this is latent; it must be fixed (Unix branch only) before SG-000115 activation.
2. `crates/orcel-provider-fs/src/lib.rs:875-878`: off Windows, workspace containment (`is_within`) is a case-sensitive component prefix, while APFS is case-insensitive by default. The Git-control guard is already case-insensitive on every OS (`eq_ignore_ascii_case(".git")` at `lib.rs:107`, `:133`, `:193`), so `.GIT` is covered. **UNVERIFIED:** whether `is_within` itself, any other protected name, or a `..namedfork/rsrc` resource-fork alias can be used to get past a guard; this must be tested on a real APFS volume.
3. `distribution/macos/README.md:30-32` tells users to run `xattr -dr com.apple.quarantine`. That removes Gatekeeper's quarantine check for the folder. Under the founder's rule (never instruct users to bypass Gatekeeper) this instruction should be replaced (section 7).
4. `crates/orcel-tunnel/src/lib.rs:237-253`: the `orcel-mcp-host` environment allowlist holds only Windows variables and `PATH`; `HOME`, which the macOS state root needs (`crates/orcel-platform/src/paths.rs:203-207`), is not passed. Not reachable on macOS today because `orcel-mcp-host` fails there: it verifies a Windows install (`crates/orcel-lifecycle/src/mcp_host.rs:62`) and `host_platform()` is `UnsupportedPlatform` off Windows (`crates/orcel-lifecycle/src/lib.rs:139-170`). It blocks M1.

## 4. Recommended minimum macOS version

**Recommendation: macOS 15.0 Sequoia, Apple Silicon (arm64), for M1 to M5. Qualify on macOS 15 and macOS 26.**

Justification, from verified code and evidence:
The floor rests on points 3 to 5. Points 1 and 2 are context, not the basis.

1. **Capture needs at least 14.0.** The vendored window capture calls `SCScreenshotManager::capture_image` (`apps/orcel-native-host/third_party/cua-driver/crates/platform-macos/src/capture.rs:542-545`); `SCScreenshotManager` is available from macOS 14 (ext, Apple documentation; not verified in this repository).
2. **SkyLight keyboard delivery needs 15.0, only if SkyLight is enabled.** The auth message selector used by the private SkyLight route exists only from macOS 15; on 14 the route guards and the event is degraded (`platform-macos/src/input/skylight.rs:605-613`, `:664-672`). That route is off by default (S-05, P-11) and enabling it is founder decision 10, so this point does not set the floor for the default public `CGEventPostToPid` route.
3. **The consent model assumes 15.** The capture-consent logic is written for the macOS 15 direct-capture alert; on 14 there is no alert and the code takes a different branch (`platform-macos/src/capture_consent.rs:93`, `:246`) that has never run on a 14 host: UNVERIFIED.
4. **All native evidence is on 26.6.2** (CI `RELEASE_READINESS.md:24`; hardware `SECURITY_INTEGRATION.md:77`). Nothing has run on 14 or 15. A floor below the oldest qualified version would be an unverified claim.
5. **The backlog already names 15 and 26** as the install acceptance matrix (`IMPLEMENTATION_BACKLOG.md:697`).
6. **The M1 core needs less** (`confstr`, `getpeereid`, `renameatx_np`, `LAContext`, `CFUserNotification`, `SecStaticCode` are older than 15, ext), so 15 costs M1 nothing while keeping one supported floor across milestones.

Enforcement: M1 sets `MACOSX_DEPLOYMENT_TARGET=15.0` for every macOS build (Rust's default for `aarch64-apple-darwin` is 11.0), so an API newer than 15 fails to link unless guarded, and a macOS 15 runner leg proves the binaries load there. If a qualified macOS 15 run fails on an M3 capability, the floor for that capability rises and the capability reports `unavailable` below it; it is never silently degraded.

Implemented by MAC-M1-01 (#834): the `rust`, `native-host`, `contain` and `macos-dev-package` jobs set the target from a macOS-only step; the `rust` job runs on `macos-15` beside `macos-latest`; `vtool -show-build` must report `minos 15.0` for the debug `orceld` (`rust`, both macOS legs) and the release `orceld` (`macos-dev-package`). This is hosted-runner evidence only; no real Mac on macOS 15 has run these binaries (UNVERIFIED on hardware).

**Intel (`x86_64-apple-darwin`):** deferred. No Intel evidence exists, the target is not installed on the development PC, and Apple said at WWDC 2025 that macOS 26 is the last release for Intel Macs (ext, UNVERIFIED here). An Intel leg is worth adding only if a hosted Intel image is available at no cost and the full M1 suite passes there. **Universal binaries:** not justified until Intel qualifies; a universal binary would ship an unqualified slice.

## 7. Zero-cost signing and distribution: research and honest limits

**What is free and lawful:**
- **Ad-hoc signing.** On Apple Silicon every native arm64 executable must carry a signature to run; the linker applies an ad-hoc one automatically, and `codesign --sign - <file>` applies one explicitly (`distribution/macos/package-dev.sh:2-8` records that the tarball's binaries carry only the linker's ad-hoc signature). An ad-hoc signature has no identity: it is a hash of the code (cdhash).
- **Source builds.** A binary built on the user's own Mac is not quarantined, so Gatekeeper's download assessment does not apply to it. `cargo build --locked` from a tagged source tree, with the checksums and provenance of that tree, is a fully zero-cost path.
- **A Homebrew tap with a source-build formula.** A formula in a tap the project owns (for example `TheHalfMoon/homebrew-orcel`) can build from the tagged source on the user's Mac. Homebrew builds are not quarantined, and no Apple account is involved. Creating that repository and publishing the formula is publishing, so it needs the founder. Inclusion in `homebrew-core` depends on Homebrew's own acceptance rules (ext, not assessed). Homebrew casks of unsigned or ad-hoc-signed apps are being phased out by Homebrew policy (ext, UNVERIFIED); a cask is therefore not the recommended path.
- **A locally generated self-signed code-signing certificate** (created on the user's own Mac) gives a stable designated requirement across that user's rebuilds, so TCC grants and Keychain ACLs would survive rebuilds on that Mac. It does not satisfy Gatekeeper for anyone else. Whether TCC honours it for a CLI binary as expected is UNVERIFIED and needs a real-Mac test before any recommendation.

**What Gatekeeper does with ad-hoc signed software (ext, to be confirmed on the founder's Mac in M5):** a quarantined download that is not Developer ID signed and notarized is blocked at first launch. On recent macOS the user can allow it only through System Settings, Privacy and Security, "Open Anyway", for that specific item; the old Control-click shortcut was removed in macOS 15 (ext). That per-item allowance is the user approving one item through the system's own flow; it is not disabling Gatekeeper. Orcel documentation may describe that system flow; it must never tell users to run `spctl --master-disable`, disable SIP, or strip quarantine to get around the check. Finding 3 (section 1) proposes replacing the current `xattr -dr com.apple.quarantine` instruction with the source-build path and the system's own per-item flow.

**Honest limits:**
- Ad-hoc signing is **never** notarization. Notarization requires a Developer ID certificate and an Apple account in the paid program. No Orcel artifact, document or release note may call an ad-hoc build "signed" without the word "ad-hoc", or "notarized" at all.
- TCC grants for ad-hoc binaries attach to the cdhash and are lost on every rebuild (`distribution/macos/README.md:58`); users re-granting to "anything named Orcel" is the S-22 risk (`SECURITY_INTEGRATION.md:56`).
- The Keychain item ACL trusts the unsigned creating binary by path and hash (`secret_store.rs:14-22`); the data-protection keychain is out of reach without a paid identity.
- XPC peer code-signing requirements, `SMAppService` login items and App Store distribution are out of reach or of little value without a stable signing identity.
- macOS packaging as written in XP-16 (signed bundle, notarization) stays blocked on FD-05 (`IMPLEMENTATION_BACKLOG.md:82`). This packet proposes a zero-cost XP-16 variant (source build plus tap plus an unsigned, ad-hoc dev tarball with checksums and provenance), which is a founder decision because it changes what "macOS package" means for M5.
