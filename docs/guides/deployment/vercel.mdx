Deploy orcel to Vercel when you want the framework’s managed build and runtime integrations. Vercel runs the web service, workflows, sandboxes, schedules, and deployment observability.

## Prepare the Vercel project

Run this from the project root to link it to a Vercel project. For an orcel agent workspace, use the workspace root, not a member directory:

```bash
orcel link
```

The command links an existing project or creates one, then pulls its environment variables. For non-interactive use, name the project instead of picking it:

```bash
orcel link --project your_project_name --non-interactive
```

Use `--team` as well when the account has access to more than one team. `orcel link` creates the project if it doesn't exist yet.

## Configure credentials and auth

A string model ID routes requests through the [Vercel AI Gateway](https://vercel.com/docs/ai-gateway). The deployment authenticates through project OpenID Connect (OIDC), so you don’t need a provider API key for that path.

Add credentials for direct model providers, tools, and connections to the Vercel project environment. Add any signing keys or passwords required by your [route authentication policy](../auth-and-route-protection). Replace `placeholderAuth()` before a browser sends a production request.

## Select the sandbox environment

The default environment selects Vercel Sandbox on Vercel. To select it explicitly:

```typescript
import { defineSandbox } from "orcel/sandbox";
import { VercelSandbox } from "orcel/sandbox/vercel";

export const environment = VercelSandbox.environment();
export default defineSandbox(() => environment.open());
```

See [Sandbox](../../sandbox) for preparation, resource limits, network policy, and lifecycle.

<Callout type="info" title="Sandbox prewarming">
  During a Vercel build, orcel creates or reuses a snapshot-backed template when an environment uses
  `VercelSandbox.environment({prepare})` or has seed files. A prewarm failure stops the deployment.
  See the [sandbox lifecycle](../../sandbox#lifecycle).
</Callout>

## Deploy the agent

For a single-agent project without a frontend, use `orcel build`. For an agent-only workspace, run it from the workspace root: orcel generates a separately built service and a `/<name>/orcel/v1/*` transport route for each member. All members deploy together in one Vercel project. See [Project Structure](../../concepts/project-structure) for workspace membership and layout rules.

A Next.js-centered project uses [`withEve` in `next.config.ts`](../frontend/nextjs) and its Next.js build command. If you author the project's broader service graph in `vercel.ts`, use the configuration below instead.

### Compose agents with other Vercel services

Use `withEve` from `orcel/vercel` when the agents and other applications are peer services. The helper contributes workspace agents to a Vercel service graph; it does not manage or require a particular frontend framework. Unlike `orcel/next`, this keeps the project lifecycle separate from Next.js. Both integrations deploy the agent services together in one Vercel project.

For a standalone agent or workspace with a peer Next.js frontend under `apps/web/`, replace `vercel.json` with a root `vercel.ts`. The frontend uses an ordinary Next.js config without `orcel/next`:

```typescript title="vercel.ts"
import { withEve } from "orcel/vercel";

export default await withEve({
  services: {
    web: {
      framework: "nextjs",
      root: "apps/web",
    },
  },
  routes: [
    {
      src: "^(.*)$",
      destination: { type: "service", service: "web" },
    },
  ],
});
```

Vercel evaluates `vercel.ts` before resolving the service graph. `withEve` adds the root agent, or every direct workspace member, as an independently built service and returns a plain Vercel configuration. Named workspace agents mount at `/orcel/<name>/v1/*`; a root agent mounts at `/orcel/v1/*`. Vercel then builds the frontend and each orcel agent separately. The frontend does not need `withEve` in its framework configuration or a build script that builds the agents.

The Web Chat installer can generate this composition for a standalone agent or a selected workspace agent. Configure authentication for every exposed agent. To self-host the same source layout, replace Vercel composition with your own [process and proxy configuration](./self-hosting#run-workspace-members).

Run Vercel CLI 59.16.0 or newer with `vercel dev --local` to start the complete service graph locally without linking a Vercel project. A generated Vercel Web Chat project exposes this as `pnpm dev:all`. When the directory is linked, Vercel also loads its development environment and settings. Use `pnpm dev` or `pnpm dev:orcel` when you want one agent and the orcel terminal UI, or `pnpm dev:web` when you want the frontend without its agent services. Named agents use the same `/orcel/<name>/v1/*` routes in development, and default `defineWorkspaceAgent` transports can call peers without deployment credentials.

Generated transport routes are inserted before a filesystem handler or, when no filesystem handler exists, before authored routes. `withEve` throws instead of overwriting an authored service key or exact transport route that belongs to a generated agent. Remove the authored route, and remove or rename the authored service; `withEve` adds both automatically. Names in the array form of `services` must also be unique. Other service names, routes, bindings, and Cron Jobs remain authored in `vercel.ts`.

Custom agent channel endpoints are not published automatically. Expose one explicitly by routing it to the generated service:

```typescript title="vercel.ts"
import { withEve } from "orcel/vercel";

export default await withEve({
  services: {
    web: { framework: "nextjs", root: "apps/web" },
  },
  routes: [
    {
      src: "^/webhooks/github$",
      destination: { type: "service", service: "orcel-triage" },
    },
    {
      src: "^(.*)$",
      destination: { type: "service", service: "web" },
    },
  ],
});
```

A Vercel project can use only one configuration source, so remove `vercel.json` when adopting `vercel.ts`. Keep `orcel` in the root package dependencies so Vercel can import `orcel/vercel` while evaluating the configuration. `withEve` discovers the workspace containing its evaluation directory, including Vercel's temporary `.vercel` configuration directory. Pass `{ root: "/absolute/workspace/path" }` as the second argument only when you need to select a specific workspace root.

An authored orcel service routed at `/orcel/v1` already uses the protocol path; callbacks remain at `/orcel/v1/callback/*`. A named mount such as `/orcel/support` adds that mount before the protocol path, giving `/orcel/support/v1/callback/*`.

### Deploy the project

Deploy the linked project to production from its root:

```bash
orcel deploy
```

`orcel deploy` installs dependencies, runs `vercel deploy --prod`, and pulls the project environment after deployment. You can also push to a Git-connected Vercel project. Hosted Vercel builds set `VERCEL`, so `orcel build` writes the deployment bundle under `.vercel/output`.

When `orcel deploy` creates a new Vercel project, it configures trace sampling so traces appear in Agent Runs automatically. See [Agent Runs](../../observability/agent-runs) for details. Pass `--no-trace-sampling` to skip this setting.

For non-interactive use, confirm the production deploy up front. `--project` links first, so a new project needs no separate `orcel link`:

```bash
orcel deploy --project your_project_name --non-interactive --yes
```

Vercel uses the generated output to configure these services:

- **Web runtime**: serves health, session, stream, channel, callback, and schedule routes
- **Vercel Workflow**: persists and resumes durable runs, with optimistic replay preconditions enabled so stale event-log snapshots reload before they can commit
- **Vercel Cron**: invokes authored schedules
- **Vercel Sandbox**: runs sandbox sessions selected by the default sandbox environment

## Verify the deployment

For a single unnamed agent, check the health route and connect the development TUI:

```bash
curl https://your_agent.vercel.app/orcel/v1/health
orcel remote connect --url https://your_agent.vercel.app
```

For a workspace agent, include its public `/orcel/<name>` mount. For example:

```bash
curl https://your_agent.vercel.app/orcel/support/v1/health
orcel remote connect --url https://your_agent.vercel.app/orcel/support
```

Set `VERCEL_AUTOMATION_BYPASS_SECRET` locally before connecting if the deployment uses Deployment Protection.
