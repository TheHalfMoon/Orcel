# Orcel Desktop — Windows foundation (read-only, plus controls that only take authority away)

**Status:** experimental native user-interface grain. This is **not a production release** and does not implement the unadopted Computer Use master plan or any newly privileged action.

This is a real Windows Presentation Foundation desktop executable built entirely with the Windows .NET Framework compiler. The preview itself needs no Electron, Chromium download, NuGet packages, Node runtime, model weights, cloud AI, hosted API, administrator privileges, or network access.

## Working features

- Native Windows desktop window with a compact conversation area, this computer's identity and the live state of the local Orcel runtime.
- Finds the per-user runtime the same way the runtime itself does (`%USERPROFILE%\.orcel\bin\orcel.exe`); never searches PATH or runs a user- or model-provided path.
- Truthful runtime states, parsed from the runtime's own JSON (`orcel status|version|doctor --json`): **not installed**, **not responding**, **incompatible response**, **status reported an error** (with the runtime's own message), or **installed** with its version, the optional ChatGPT tunnel's state (not configured / running / degraded / not running), detail and workspace count. Local MCP clients start Orcel themselves, so the tunnel not running never means Orcel is down. Where there's an obvious next step (install with `.\orcel.exe install`, add a workspace, refresh, match the release), the status message names it. The tunnel's detail is shown except when no tunnel is configured and there's no supervisor record at all. The runtime's own error text is shown on one line, with control and bidi characters replaced. An error or unparsable answer is never shown as healthy.
- Read-only commands: `help`, `status`, `version`, `doctor` (health-check summary with the failing and warning checks), `devices`, `files`, `tasks`, `recovery`, `history`, `clients`, `setup`, `previews`. Anything else is refused without action; chat text is never passed to an interpreter, operating-system command or AI service.
- Connect a client (`connect`): the setup to paste into Claude Desktop, Claude Code, Codex or another stdio MCP client, with this install's exact `orcel.exe` path (escaped for JSON and TOML, single-quoted for PowerShell so nothing in it expands; Claude Code is added for every folder with `--scope user`, and the Codex block carries the qualified example's timeouts), shown in a read-only text box so it can be selected and copied. A screen reader hears a short pointer to the box rather than the JSON, and the mouse wheel still scrolls the transcript over it. It runs nothing and edits no client's settings; every change a client asks for still needs approval in Orcel's own prompt.
- Workspaces (`workspaces`): the folders Orcel may use and whether each is trusted for STRONG operations, through `orcel workspace list --json` (up to 20 shown, escaped). The runtime asks orceld about each folder's trust while holding its lifecycle lock, so the app waits up to 90 s and may wait behind another Orcel command. The app never adds, removes or trusts a folder: granting a folder stays in a terminal.
- Stop controls, which only take authority away; the app never grants anything:
  - **Stop desktop control** (a red button with a stop mark in the runtime card, or `stop control`; in high contrast it uses the window colours with a heavy border, apart from the filled buttons): ends Orcel's Full User desktop control at once, through `orcel full-control revoke --json`. Granting it stays in a terminal (`orcel full-control grant`), behind Windows Hello. `control` shows whether it is active.
  - **Stop newest task** (a red button in the runtime card, or `stop task`; F4 slice 5, founder decision of 2026-11-13, #446): ends the newest report task of the current orceld run that can still be stopped (`observed`, `proposed` or `approval_denied`, owned by this run; never another session's or an earlier run's, and never one that is writing), through the app API's `task.stop`. The app then reads the task back with `task.get` and shows only orceld's state: "Control is back with you: no agent input is pending, and this added no authority" appears only when orceld says `stopped`; otherwise the app names the state it found. Bare `stop` is not a command, so it is never guessed between this and `stop control`. If the task's approval prompt is open, the Windows message box stays on screen; answering it does nothing, and the commit is refused (`ORCEL_APP_API_1.md`, section 4).
  - **`revoke all`**: an emergency revoke through `orcel emergency-revoke --json`. The runtime asks for Windows Hello itself; on success every pending approval, desktop control and every remote session lease is invalid. The app waits up to 200 s for the Hello prompt.
  - One run at a time: a second click or a repeated `stop control`, `stop task`, `revoke all`, `previews sizes` or `workspaces` while one is running is answered with "already running", so it can't start a second Windows Hello prompt or queue a second wait on the runtime's lock.
  - Each reports only what the runtime answered: a stop or revoke that isn't confirmed says so and names the terminal command, and a timeout says it may or may not have happened.
- One setting: `previews sizes` makes approval prompts show sizes only, never content, through the runtime's own `orcel approvals previews sizes --json`, with those fixed arguments only. It changes one field in Orcel's protected configuration, the same as typing the command, and nothing else; the app reports only what the runtime answered, including its own refusal. `previews` alone shows the current choice. The app never asks for more disclosure: `previews content` is answered with the terminal command to run instead, so a stray click or an automated agent typing into the app can't loosen what prompts show. Sessions started afterwards use the setting, so restart AI clients after a change.
- Approval history (`history`): the newest ten approval decisions orceld recorded, newest first, through the same read-only app API (`approval.history`): when, approved or denied, SOFT or STRONG, the workspace, whether it was used or was an emergency revoke, and where the request came from (this computer, or REMOTE with its provider and device; "origin not recorded" for decisions made before origins were recorded). It never names what was approved. When the runtime reports the history as anything but verified (busy or unavailable, or failing its integrity check), the app says the list is the last checked view and may miss recent decisions. Fields are shown escaped like task titles, so none can add a line. The app reads the history only; approvals are answered in the system's own prompt. As with tasks, a same-user process that served the pipe first could show an invented history, though nothing it shows can act.
- Settings (`settings`): Orcel's current settings in one place: approval previews, desktop control, how many folders it may use and how many AI clients are connected, each with where it is changed. It reads only, through the same fixed queries `previews`, `control` and `workspaces` run and `clients.list`, and words each in its own read-only terms; a value it can't read (no answer, an error) is shown as "couldn't check", never guessed. Sizes-only previews stay their own command, and everything that grants something stays in a terminal.
- Guided start (`setup`): a four-step checklist (install Orcel for this Windows user, connect an AI client, choose a folder with `orcel workspace add`, try it) that says what is done and names the next step. It reads whether Orcel is installed, whether `clients.list` shows a connected client, how many folders the same read-only `orcel workspace list --json` the `workspaces` command runs reports, and whether the approval history or task list shows Orcel has done anything; a check that can't answer is said to be unknown, never guessed. It appears by itself when the app opens only while Orcel isn't installed (afterwards a closed client looks the same as one never set up), and whenever you type `setup`. It reads only; each step is the person's to take (the app never installs anything or edits a client's settings).
- Recovery (`recovery`): when orceld stops while it is writing an approved report, the next orceld checks the destination and records what it found on the task. `recovery` reads the newest ten tasks through the same app API (`task.list`, `task.get`) and says, for each one that was checked: the report is there and verifies, nothing was written (ask the client to run it again), or a file is there (or couldn't be read) that doesn't check (Orcel can't tell what happened, won't retry, and you should check it yourself). The count of reports needing attention comes first; tasks whose details couldn't be read are counted and never taken as "not interrupted". Titles and paths are escaped like task titles. It reads only and never retries or deletes anything.
- Connected AI clients (`clients`): the local AI clients (Claude Desktop, Claude Code, Codex and others) whose Orcel session is running now, newest first, through the read-only app API (`clients.list`): the name and version each client reported, how it connects, since when, and its workspace. Names are what the client said about itself and are marked not verified; any local program could claim any name. Fields are shown escaped like task titles. A client using an older Orcel isn't listed, so an empty list doesn't prove nothing is connected. The app can't disconnect a client; closing the client ends its session.
- Report task timeline (`tasks`, SG-000127): reads the current orceld run's report tasks through orceld's local app API (`orcel-app-api/1`, this user's pipe `\\.\pipe\orcel-<user SID>-app`): the newest five with their state, report destination and steps. Only `task.list`, `task.get`, `task.stop` (Stop newest task, above), `approval.history` and `clients.list`, one bounded request per connection, and the long-lived `events.subscribe` (see Live task updates) are ever sent. Every frame is at most 64 KiB, newline included; the two reads have 4 s in all per call: on timeout the pipe is closed, which cancels the read. Before reading, the app checks that the process serving the pipe runs as this user at Medium integrity or above (`GetNamedPipeServerProcessId` and its token, as `ORCEL_APP_API_1.md` section 7 asks); the pipe name is predictable, so another same-user process at normal integrity could still serve it first and show invented task states (the app connects as an identification-only client; apart from `task.stop`, which a squatter could only fake the answer to, it sends nothing that acts). The check reads the server's process id and then opens that process, so a pipe whose creating process exited while another kept its handle could, in a narrow race, be attributed to an unrelated process of this user that reused the id. orceld's state is shown before the planner's title. Titles and paths come from the planner and the workspace: line, paragraph and bidi control characters are replaced and a title cannot close its quotes. When the pipe does not answer or answers unusably, the app says so and shows no tasks. The app cannot start or approve a task, and stops one only on Stop newest task or `stop task`; it reads once per `tasks` command, and follows `task.updated` events as described below.
- Shell and process sessions are labelled **unavailable** (not armed in this build).
- Runtime queries run off the UI thread with both output streams drained concurrently (no full-pipe deadlock), output bounded to 256 KB, and the child placed in a kill-on-close Job Object: on timeout (8 s; 30 s for `doctor`, which starts the daemon for an IPC probe) the job is terminated, and descendants still alive when a query ends are killed with it. Processes started in the few milliseconds before the child joins the job are not covered; if no job can be created, only the direct child is killed on timeout. A failed query is reported as such; it never crashes the window.
- The runtime is located only through a drive-qualified `%USERPROFILE%` (UNC and drive-relative values are ignored).
- Folder preview: a user-selected folder is enumerated off the UI thread without materializing the directory and limited to 12 names; the app stops waiting after 10 s even if the file system never answers (for example a stalled network share; the abandoned enumeration may keep one thread blocked until the file system returns); nothing is modified or uploaded.
- Accessible controls: UI Automation ids and names on the window, command box, Send/Refresh buttons, transcript, runtime and device state; keyboard focus starts in the command box.
- Orcel AI, voice and pairing are shown as **not connected**; no remote devices are fabricated.

## Build and test

Run these in a regular, non-elevated Windows PowerShell session from the repository root:

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\apps\orcel-desktop-preview\tests\verify.ps1
    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\apps\orcel-desktop-preview\tests\e2e.ps1
    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\apps\orcel-desktop-preview\tests\e2e.ps1 -RuntimeRoot <isolated USERPROFILE with an installed runtime>

`verify.ps1` compiles the application with the in-box .NET Framework compiler and runs the self-tests: command allowlist and refusal of shell-shaped input, interpretation of real runtime JSON (installed, timeout, garbage, error, doctor failures, version), a stalled child stopped at its timeout, a child flooding both streams drained without deadlock and bounded, and the bounded, cancellable folder preview.

`e2e-tasks.ps1 -Orceld <path to orceld.exe>` starts a real orceld on an isolated app API instance, workspace and state (under the profile root by default: orceld refuses a state path with an ancestor another user can change), drives `report/start` and `report/preview` over its stdio channel (nothing reaches the approval broker), runs `e2e.ps1` against that instance, requires the app to show the live task, and checks that nothing was written.

`e2e.ps1` is a native Windows end-to-end test driven through Windows UI Automation (no third-party framework). It launches the real executable with an isolated `USERPROFILE` (an empty temporary folder by default, or `-RuntimeRoot` for a real test install), checks the runtime panel and initial keyboard focus, sends `status`, a shell-like string (must be refused and the app must start no child process afterwards), and with `-RuntimeRoot` also `doctor` and `version`; it checks accessible names and keyboard focusability, measures startup and memory, and closes the window. The user's real install is never queried.

Measured on Windows 11 build 26300 (Intel UHD Graphics, 120 DPI, 1536×960), single runs: executable 43,008 bytes; window in 443–810 ms; live runtime status in 512–858 ms; `doctor` against a real install about 8 s. Memory there: about 149 MB working set / 145 MB private idle, about 228 MB / 211 MB after runtime queries.

**Memory against a minimal WPF window (#288).** `tests/memory.ps1` builds a minimal WPF window the same way (`tests/baseline/MinimalWindow.cs`) and profiles both on the same machine. The Rust CI job runs it on its Windows runner and prints `WPF-MEM` lines; it is report only, with no budget, and it refuses to run outside CI unless `-AllowLocal` is given, so it never opens windows on a person's desktop. All generated binaries go to the user's TEMP directory. A signed installer and installed-size qualification have not been performed.

## Accessibility

- **High contrast:** when Windows high contrast is on, the app uses the system's own window, text, highlight and highlighted-text colours instead of its dark palette. Buttons use the highlight pair. It reads the setting when it starts, so a change applies the next time it opens.
- **Screen readers:** each reply is announced through a polite live region (UI Automation `LiveSetting`), cut at 400 characters, without moving focus from the command box. The app turns off .NET Framework's legacy accessibility behaviour at start (`Switch.UseLegacyAccessibilityFeatures`), which would otherwise hide live regions in a build with no target framework. The command box, Send, Refresh status, Stop desktop control, the transcript and the runtime state each have an accessible name and automation id.
- **Keyboard:** focus starts in the command box, and Enter sends. The end-to-end test (`tests/e2e.ps1`, run under UI Automation on CI's Windows runner) checks that focus starts there, that the command box, Send, Refresh status and Stop desktop control can take keyboard focus, and that a reply reaches the announcement element. The self-test checks that element is set up as a polite live region. The managed UI Automation client CI uses can't read `LiveSetting`, so whether WPF exposes it and a screen reader speaks it still needs a person (Narrator, NVDA, or Accessibility Insights).
- **Not yet checked:** a real Narrator or NVDA session, 150% and 200% scaling, and right-to-left text. Those need a person at a Windows desktop.

## Security boundary

The preview's only connection to orceld besides the fixed CLI queries is the read-only app API pipe (this user's local pipe, whose server must run as this user; no network). The preview does not create a network listener, model connection, browser automation service, input actuation, shell execution API, file mutation (other than the runtime's own CLI saving the sizes-only preview setting and recording a desktop control revoke or an emergency revoke in its protected state), remote pairing endpoint, or delegated approval. It never attempts to elevate privileges.

Only fixed CLI operations may be invoked from the known per-user installation path: the read-only queries, and three that only take authority away: `approvals previews sizes`, `full-control revoke` and `emergency-revoke`. The existing Orcel/Orcel core remains the policy authority; the preview does not duplicate its grants or bypass local approvals.

Security finding #278 remains open and blocks promotion of ledger-backed production actions until independent qualification.

2. Integrate a reviewed read-only status IPC instead of repeatedly spawning the compatibility CLI.
3. Adopt the existing authorization broker before any action preview/approval/execution UI.
4. Build secure multi-device enrollment/status and revocation, with no default raw remote control.
5. Design cloud-only Orcel AI API integration with authenticated task IDs, user-granted screen/data sharing and explicit model unavailability, then add voice.
6. Prove native E2E, signed delivery, security review, independent tests, product packaging and installer/download size before release.

## Live task updates

The app follows `orceld`'s `task.updated` events over the read-only app API and shows each as it happens, so "report proposed, waiting for approval" appears without typing `tasks`. Once subscribed it sends nothing more, and each connection checks that the server is this user at normal integrity. What happened before the app started isn't announced: `tasks` shows it. If updates may have been missed, such as when `orceld` restarts or the app falls behind, it says so and shows the current list instead. CI runs this against a real `orceld` under UI Automation on a hosted runner.
